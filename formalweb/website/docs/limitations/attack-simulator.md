# 攻撃シミュレーターの前提と限界

※この画面の量子コンピューター・被害者・サービスは、すべてこのPCの中の仮想環境です。実機やクラウドサービスには一切接続しません。

攻撃シミュレーターは、宣言したサービス条件と物理モデルの下で、仮想環境内の操作と結果を確認するための機能です。

このページは**2026年10月7日時点のdesktop／development向け製品profile**を説明します。自由モードでは、設定から環境を作成し、回路送信・待機・結果照会・破棄まで操作できます。Reset漏洩の課題は準備中で、まだ選択できません。公開用profileでは攻撃シミュレーターのAPI・WebSocketは有効になりません。

Gate-awareやPulse-levelの制限は、別ページの[現在の制限事項](./current-limitations.md)を参照してください。

## 設定と攻撃者の操作の境界

最初に自由モードか課題モードを選び、その後で設定を行います。自由モードで変更できるのはサーバーの設定目録に登録された項目だけです。課題モードでは、課題presetが設定を固定・秘匿でき、編集可能な項目もpresetで決まります。

環境成立時には、選んだ値と値ごとの根拠（basis）をmanifestへ凍結します。成立後に、権限・物理条件・サービス条件を変更することはできません。設定を変える場合は、環境を破棄して作り直します。

温度・磁束ノイズ・qubit周波数などの設定は、仮想世界を作る際の前提条件です。これらを設定できることは、環境内の攻撃者が実機の温度や周波数を変更できることを意味しません。ブラウザから権限・資格情報・manifest・根拠を直接指定することもできません。

## 設定項目の根拠

各設定項目の根拠は、操作画面には表示せず、このページにだけ記載します。環境成立時には、選んだ値と根拠をmanifestへ凍結します。

| 項目 | 根拠 |
|---|---|
| 抽象コマンド: 交互観測 | 現実のサービスには無い操作です。初期値はオフです。オンにすると、攻撃者のジョブに`submit --interleave`を付けて、被害者の実行を各shotの直前に挟めます。 |
| 抽象コマンド: 被害者の動きの表示 | 現実のサービスには無い操作です。初期値はオフです。オンにすると、交互観測のジョブのあとに`activity`（または画面の「被害者の動き」）で、shotごとの「被害者の実行 → サービスのReset → 攻撃者の測定」の順番と世界時刻を読めます。自由モード専用で、課題モードでは使えません。 |
| 被害者の秘密bit | 被害者が毎回準備して測定する1 qubitの値です。自由モードでは見て変更できます。課題モードでは非公開になります。 |
| 1回の観測で攻撃者が繰り返せる回数 | 攻撃者が1回の観測要求で、被害者の実行の直後に自分の測定を挟める回数の上限です。ホストの計算量を守るための上限でもあります。 |
| 配置の方針 | シナリオが決める配置の条件です。現実のクラウドの配置保証ではありません。 |
| 交代時のReset回数 | 利用者が交代するときにサービスが行うResetの回数です。shotごとのResetではありません。 |
| 被害者の操作時間 | シミュレーターが仮定した時間です。スナップショットの較正値ではありません。 |
| サービスの処理遅延、結果公開の遅延、拒否応答の遅延、制御操作の処理遅延・応答遅延 | 仮想環境の中の遅延です。PCの処理時間とは別です。 |
| 受付までの通信遅延 | 仮想環境の中の遅延です。PCの処理時間や実際の通信時間とは別です。 |
| 計算の再利用の許容誤差 | 計算を速くするための近似の精度で、実サービスの性質ではありません。同じジョブのshotは、不完全なResetが前の結果の記憶を残すため入口の状態が少しずつ違いますが、前のshotと入口の状態の差（トレース距離）がこの値以内なら、その計算を再利用します。物理過程は入口状態の距離を増やさないので、再利用による誤差は、1shotあたりこの値以内、ジョブ全体の測定結果の分布で、shot数×この値以内に収まります。初期値は1e-5（1024 shotでも上限は1%）、0は厳密（同じ状態のときだけ再利用）です。Grover回路の測定では、約半分のshotの計算を省けました。 |
| shot間の待機 | 回路を繰り返すとき、前のshotと次のshotの間に置く待機です。クラウドQPUが回路の間に入れる待機（IBMでは`rep_delay`）を模したもので、公開資料に採用できる値が無いため、初期値は0（待機なし）で、実サービスの値ではありません。0より大きくすると、待機のあいだ前のshotの状態がT1・Tφで緩和します（状態を引き継ぐ実行で効きます）。最後のshotの後ろには置かず、交代時の待機はジョブ間の待機として別に扱います。交互観測（抽象コマンド）では使えません。 |
| 計算が追いつくまで時計を止める | PCの計算の遅れを補う任意の設定です。初期値はオフです。 |
| qubitごとのReset成功確率 | サービスが交代時に行うResetが\|0⟩に戻す確率です。スナップショットの読み出し誤差から導いた近似値が初期値で、実測値ではありません。値を下げるほど前の利用者の状態が残ります。 |
| qubitごとのT1・T2 | スナップショット（2026-04-15）の値です。現在の実機の代表値ではありません。 |
| qubitごとの熱励起の割合 | スナップショットに値がないため、変更できる仮定として0を置いています。 |
| デバイス品質、温度、磁束ノイズ、qubit周波数、T1の上限、Tφの上限 | 本体シミュレーターと同じ物理モデルへの入力です。スナップショットの較正値ではありません。 |

## 遅延命令

回路には、量子ビットを一定時間だけ待たせる遅延を書けます。Qiskitの`delay`やOpenQASM 3の`delay`に相当するもので、回路の形式では継続時間（マイクロ秒）を指定した恒等ゲート`I`として表します。Pythonからは`Circuit.delay(qubit, duration_us)`で書けます。

- 指定した量子ビットだけが、その時間、T1とTφによる緩和を受けます。ほかの量子ビットには作用しません。
- 同じ列に並べたゲートは並列に進み、その列の長さは最も長い継続時間になります。
- 1つの遅延は0〜10,000マイクロ秒です。
- 実機ではゲートの間で空いている量子ビットも自然に緩和しますが、このシミュレーターが待機として扱うのは、明示した遅延だけです。実機にある遅延の粒度による丸めも再現しません。

## Pythonで回路を書くときの時間の扱い

`Circuit`でゲートを積むと、別の量子ビットのゲートは同じ列に並んで並列に進みます（実サービスのトランスパイラが行う詰め直しと同じ扱いです）。同じ量子ビットを使うゲートは、書いた順に別の列へ進みます。測定は最後の1列にまとまり、同時に行われます。測定した量子ビットを、その後のゲートで使うことはできません。

回路の列数は200、ゲート数は800が上限です。「shot数×命令数」にも上限があり、超えたときのエラーには、その回路で送れる最大のshot数が示されます。この上限は計算量を守るためのもので、模擬しているサービスの性質ではありません。

回路は、利用できるゲートと量子ビットの結合に合わせて自分で用意する必要があります（トランスパイラは含みません）。論理量子ビットの番号は、領域の物理量子ビットに先頭から順に対応します。

## 世界時刻と実時間

製品profileは、**明示的な待機だけで世界時刻を進める方式（explicit_wait）**を使います。回路送信・取消・状態照会・結果照会だけでは世界時刻は進みません。時間を指定した待機、自分の要求への応答待ち、最も早い自分の応答までの待機で進めます。

被害者の宣言済み動作、サービス処理、物理モデルは、その進行区間で動きます。ユーザーが考えている実時間や、PCの数値計算・描画の遅れを、QPUの物理時間へ加算しません。これは現実のクラウドがユーザーの操作を待って停止するという主張ではなく、実行基盤の性能差を攻撃条件へ混入させないための方式です。

初期profileの追加通信・サービス処理・公開・制御delayは0 µsです。これらは変更可能な仮想サービスの設定であり、実サービスの通信時間を測定した値ではありません。ゲート・測定・Resetの所要時間とは別に扱います。

一回の待機には、仮想時間1,000,000 µsと進行128ステップの上限があります。上限到達は待機の制限として返し、物理的な攻撃失敗へ読み替えません。後述の環境の有効期限は実時間で管理されるため、世界時刻が停止していても期限は進みます。

## 較正データの出所と規模

初期値の出所は、`qiskit-ibm-runtime` 0.50.0に同梱された`ibm_kingston`の較正スナップショットです。較正時点は**2026年4月15日09:15:15（UTC+02:00）**です。元のJSONは改変せず、読み込み時に出所記録のSHA-256と照合します。データのライセンスはApache-2.0で、Qiskitを本体の計算依存には加えていません。

:::note[歴史的な値と現在の実機は別です]
スナップショットはある時点の装置の値です。現在の実機の代表値でも、今後の計算結果を保証する較正値でもありません。2026年8月3日のqubit 150の値を、全qubitへ均一に当てる方式は使いません。
:::

| 項目 | 現行profileの範囲 |
|---|---|
| 仮想QPUのトポロジー | 156 qubit、物理結合176本（有向coupling mapの352件） |
| 状態を保持・計算する領域 | 共用配置では6 qubit、別領域配置では互いに重ならない6 qubit領域を二つ（結合状態の12 qubit計算はしない） |
| 初期保持領域の物理ID | 2、3、4、16、5、23 |
| 別領域配置の追加物理ID | 6、7、8、17、9、27 |
| 初期状態 | 保持領域全体が $\lvert0\cdots0\rangle$ |
| 回路の幅 | 最大6 qubit |
| shots | 一つのProgramで最大1024 |
| 命令の実行回数 | shotsを含めて最大32768（shots × 命令数） |

156 qubitすべての共同量子状態を計算しているわけではありません。トポロジーの規模と、密度行列を保持する領域のメモリ上限を分けています。二つの領域を選ぶ場合も、各6 qubitの状態を別々に保持します。配置可能と表示されたすべてのqubitを自由に選べる機能ではありません。

読み出し誤差が10%を超えるqubit、またはCZ誤差が0.5以上の結合に属するqubitは配置対象から外します。必要なT1/T2や測定・Reset所要時間が欠落したqubitも除外し、目録には理由を表示します。qubit 146にはT1/T2がなく、代わりの値を作りません。これらの判定は、記録された配置方針であって実機の利用可否を現在判定したものではありません。

## 待機ノイズの二つの入力方式

二方式は排他です。選ばなかった方式の値を重ねて使いません。

| 方式 | 入力と扱い |
|---|---|
| 実機較正値（初期選択） | 保持qubitごとのスナップショットのT1・T2を初期値とし、熱平衡の励起状態占有率を直接指定します。温度・磁束ノイズは追加しません |
| 物理パラメタ | 温度・qubit周波数・磁束ノイズ・デバイス品質などから、本体と同じ既存の環境モデルで崩壊率を導出します。待機率にはスナップショットのT1/T2を使いません |

較正値方式の純粋な位相緩和時間は、$1/T_\phi=1/T_2-1/(2T_1)$から導出します。熱平衡の励起状態占有率の初期値0は、スナップショットで測定された値ではなく、変更可能な仮定です。

物理パラメタ方式では、導出した下向き・上向き緩和率と位相緩和率から、$T_1=1/(\gamma_\downarrow+\gamma_\uparrow)$、$T_\phi=1/\gamma_\phi$、熱平衡占有率$\gamma_\uparrow/(\gamma_\downarrow+\gamma_\uparrow)$を求めます。周波数はスナップショットに含まれないため、ユーザーの明示入力を必須とし、乱数で割り当てません。

磁束ノイズの式は周波数可変transmonを想定した現象論です。固定周波数の実機qubitへそのまま適用できるとは限りません。物理パラメタ方式でも、トポロジー・CZ・読み出し・Resetのデータは同じスナップショットを使います。「スナップショットを使わない」のは待機ノイズの率の導出部分です。

待機モデルは独立な定数率の緩和・位相緩和です。この製品経路の待機モデルは、ZZ結合・駆動クロストーク・時間ドリフトを再現しません。

## Reset・ゲート誤差・所要時間の近似

Reset成功確率$P_{\mathrm{reset}}$は、qubitごとの読み出し割り当て誤差から

$$
P_{\mathrm{reset}}=1-\frac{P(1\mid0)+P(0\mid1)}{2}
$$

と導く近似です。**直接測定されたReset成功率ではありません。** Resetの目標状態は計算基底の $\lvert0\rangle$ です。初期profileのReset回数1はサービスの主体交代時の設定であり、実サービスが各shotで必ず同じResetを行うという主張ではありません。

利用者交代時のReset前測定は、対象qubitを測定してから条件付きXでResetするモデル選択です。参照した実サービスが利用者交代のたびにこの手順を実施するという証拠ではありません。

自由モードでは配置条件を成立前に選べます。「同じ領域」は被害者・攻撃者が初期の同じ6 qubitを順番に使い、交代時のResetと状態残留を扱います。「別領域」は被害者に初期領域、攻撃者に追加領域を割り当て、各領域の状態を非アクティブ中も保持し、その間の宣言された待機ノイズを反映します。どちらも一つのFIFOでジョブを処理し、領域が分かれても同時実行にはなりません。別領域間のZZ・クロストークは現行の待機モデルでは再現しません。この二択はシナリオ上の条件であり、**現実のクラウドにおける配置保証ではありません**。課題モードではpresetが条件を固定できます。成立時に選択値と根拠をmanifestへ凍結し、成立後は変更できません。

CZの`gate_error`は平均ゲート不忠実度$r$として扱います。シミュレーターでは、対象の二量子ビットを完全混合状態へ置換するチャネルの確率を$p=4r/3$とします（次元$d=4$、$r=p(d-1)/d$）。この対応は選んだ近似チャネルの平均不忠実度を合わせるもので、誤差指標から実機のノイズチャネルを一意に同定したものではありません。

単一qubitゲートは、次の分解に含まれる`rz`・`sx`・`x`の所要時間を、対象qubitのスナップショットから足し合わせます。このスナップショットでは`rz`は0、`sx`と`x`は全qubitで32 nsです。一律に0.032 µsを割り当てる方式ではありません。

| ゲート | 所要時間・誤差を数える分解 | このスナップショットでの所要時間 |
|---|---|---|
| Z・S・T・RZ | rz | 0 |
| X | x | 0.032 µs |
| H | rz・sx・rz | 0.032 µs |
| Y | x・rz | 0.032 µs |
| RX・RY（任意角） | rz・sx・rz・sx・rz | 0.064 µs |

`sx`・`x`の平均ゲート不忠実度$r$から、単一qubitの完全混合置換チャネル確率$p=2r$を求めます（$d=2$）。分解に含まれる回数分を適用し、`rz`には誤差を入れません。同じ`sx`を二回使う場合、合成した確率は$1-(1-2r)^2$で、単純に確率を二倍にはしません。このチャネルは局所的な理想ゲートと可換なので、ゲート内部に別の物理発展を置かない現行モデルでは厳密に合成できます。これは採用した近似チャネルの計算上の等価性であり、実機のパルス列やノイズを同定したことは意味しません。準備状態を作るX・Hにも同じ規則を使います。

CZの誤差と所要時間は、引き続き結合ごとの元データを使います。同時に測定・Resetする際の共通所要時間は、対象qubitの個別所要時間の最大値です。これはシミュレーターの集約規則で、実サービスの同時実行時間を保証しません。被害者操作の1 µsは、この製品profileに明示した仮の時間であり、スナップショットの較正値ではありません。

## ブラウザ所有者・資格情報・環境の寿命

実際のブラウザ所有者と、仮想QPUサービス内の攻撃者は別の層です。所有者は環境ごとのHttpOnly cookieで識別し、サーバーは所有者識別子のhashだけを保持します。cookieは`SameSite=Strict`、`Path=/api/attack`で、HTTPSの場合に`Secure`を付けます。接続時はOriginとHostを検査し、状態変更HTTPには専用headerも要求します。

攻撃者の資格情報はシミュレーターが発行する仮想資格情報です。作成に成功したブラウザへ渡し、通信clientの内部だけで保持します。被害者の資格情報は応答へ出しません。実サービスのAPIキーを用意する機能ではありません。

| 項目 | 現在の起動設定 |
|---|---|
| 一つのブラウザの環境数 | 一般の既定値は1。desktop／developmentは明示的に4 |
| サーバー全体の環境数 | 既定値8 |
| 無操作期限 | 所有者を確認する通信がない状態で30分 |
| 作成からの絶対期限 | 24時間 |

環境数と期限は仮の運用設定です。上限到達時は新規作成を拒否し、既存環境を勝手に壊しません。破棄または期限到達で接続・世界・controllerを閉じ、枠を返します。

この所有者管理は登録・ログインを伴わない匿名方式です。全cookieを消去するとブラウザの識別は引き継げません。環境登録はプロセス内にあり、複数worker間の共有や再起動後の復元には対応していません。ページ再読み込み後の所有環境の発見と、仮想資格情報の再受け渡しも未実装です。

## 検証済みの範囲と残る作業

desktopのソース起動環境で、較正値方式・物理パラメタ方式の双方について、作成→接続→回路送信→待機→結果照会→reply受領→破棄をブラウザで確認しています。CZの平均不忠実度の写像や、スナップショットの照合にも試験があります。これは共通経路と近似モデルの動作確認であり、実機での攻撃成功や情報窃取を実証したものではありません。

Reset漏洩課題のpreset・採点器・被害者の共通Programへの接続は残っています。自由モードの操作経路が動くことと、課題を攻略・採点できることは区別します。

また、スナップショットを含むmanifestは設定ノード数の上限に近く、多数の値を同時変更すると根拠metadataの追加によって環境成立が拒否される場合があります。許可された項目をすべて同時に変更できるようにするための圧縮・資源契約は残る作業です。

公開基盤でのAPI・WebSocket中継、複数プロセスでの運用、課題の完成は、このdesktop／development向け実装の完了範囲に含みません。[今後の予定](./roadmap.md)も参照してください。
