# Yuragi-Striderとは

Yuragi-Striderの主な体験は、仮想量子サービスを攻撃者の立場から操作し、共有環境での干渉や情報漏れを調べる**攻撃シミュレーター**です。
ホーム画面の最初の入口も攻撃シミュレーターにしています。攻撃対象となる量子状態の動きを詳しく学ぶため、Gate-aware回路シミュレーターとPulse制御シミュレーターも用意しています。2つの物理シミュレーターはホームとナビゲーションの「物理エンジンを試す」にまとめています。

物理シミュレーターでは、超伝導型量子コンピューターを想定した量子回路を開放量子系として扱い、ゲート実行中の環境ノイズや制御パルスに対する量子状態の変化を可視化します。物理エンジン自体の仕様は従来どおりです。

## 物理エンジンの役割

従来の量子回路シミュレーターは理想的なものが多く、現実の環境が生むノイズや誤差を無視しています。

専用のライブラリを使えば開放量子系のシミュレート自体は可能ですが、そこには次の問題がありました。

- 入力をハミルトニアンや崩壊演算子の形で与える必要があり、実際の温度や磁束ノイズとの対応付けが難しい
- GUIを持たず、コードを書かなければ試せない
- 状態がどう崩れていくかを直観的に確かめる手段が乏しい

物理エンジンは、この3点をまとめて扱います。GUI上で量子回路を組み、温度や磁束ノイズといった**物理量そのものの単位**で環境を指定すると、開放量子系としての時間発展が計算され、密度行列・Fidelity・Purity・出力確率などの形で結果が返ります。これは攻撃シミュレーターとは独立した機能です。

## 名前の由来

**Yuragi(ゆらぎ)** は量子系が環境から受ける揺らぎ・ノイズを、**Strider(大股で歩く者)** はアルゴリズムから実機の物理まで一段ずつ降りて歩いていく体験を表しています。

## 降りていける層

物理エンジンでは、次の層をたどれます。攻撃シミュレーターはこれらのモデルを操作するものではなく、別の仮想サービス環境で攻撃者の権限や共有状態を扱います。

```text
量子アルゴリズム            Grover探索、量子テレポーテーション …
      ↓
量子ゲート                  H, CNOT, Rz …
      ↓
ゲート時間と環境ノイズ      Gate-awareモデル（温度・磁束ノイズ・T1・Tφ）
      ↓
量子状態の時間発展          密度行列 ρ(t)、Fidelity、Purity
      ↓
実機を動かす制御パルス      Pulse-levelモデル（包絡線・DRAG・リーケージ）
```

物理エンジンの2つの入口は、ゲート列から見る Gate-aware と、制御波形から見る Pulse-level です。攻撃シミュレーターとは目的と実行環境を分けています。

## 既存ツールとの位置づけ

実装している物理モデル——Lindblad型の開放系時間発展、CPTP写像、回転波近似下の駆動トランズモンモデル——は、**いずれも量子光学・量子情報の分野で確立された既知のもの**です。新しい物理法則を提案するものではありません。

本ツールが埋めようとしているのは、モデルそのものではなく**そこへ到達する経路**です。

| | 理想回路の学習 | 環境ノイズ・寿命 | 制御パルス | GUI |
|---|---|---|---|---|
| 教育用の理想回路シミュレーター | ◎ | ✕ | ✕ | ◎ |
| クラウド量子計算のコンポーザー | ◎ | △ | ✕ | △ |
| 研究用ライブラリ(QuTiP、Qiskit Dynamics 等) | ◎ | ◎ | ◎ | ✕ |
| **Yuragi-Strider** | ◎ | ◎ | ◎ | **◎** |

### QuTiPとの関係

**QuTiPは検証専用であり、本番計算には一切使用しません。** Lindbladソルバーは独自実装(Python/NumPy + Rust)です。両者は、そもそも受け取る量の抽象度が異なります。

| | 研究用ライブラリに与える入力 | Yuragi-Striderに与える入力 |
|---|---|---|
| 環境 | 崩壊演算子と緩和レート(**すでに物理から数式へ翻訳し終えた量**) | 温度[mK]、磁束ノイズ[Φ₀]、量子ビット周波数[GHz]、$T_1$/$T_\phi$(**装置の側の量**) |
| 制御 | ハミルトニアンと包絡線関数をコードで記述 | GUI上でゲート列またはパルス波形を配置 |

この**物理量から緩和レートへの変換層**自体が独自の実装であり、検証対象でもあります([入力モデルの検証](../physics-model/validations/input.md))。

ソルバーを自作している理由は速度だけではありません。既存ソルバーは「最終状態を正しく返すこと」に最適化されていますが、本ツールが見せたいのは**途中経過そのもの**です。各時刻の密度行列・Fidelity・Purity・確率分布を揃った形で取り出し、ゲート列の境界や測定の瞬間に印を付け、複数のグラフが同じ物理時刻を指したまま動く——その出力形式をソルバー側から設計しています([出力](../physics-model/outputs.md))。

そして自作しているからこそ、独立ライブラリとの突き合わせに意味があります。QuTiPを内部で呼んでいるなら、QuTiPと一致するのは当然で、検証になりません。

## 検証について

出力が物理的に妥当であることは自明ではないため、次の4層で検証し、結果はすべて機械可読な形で `validation_results/` に公開しています。

| 層 | 内容 | 参照 |
|---|---|---|
| 解析解との比較 | 厳密解が存在する状況(ゼロ散逸、指数減衰、有限温度平衡、共鳴回転)との突き合わせ | [入力モデル](../physics-model/validations/input.md) / [時間発展](../physics-model/validations/propagation.md) |
| 独立ソルバーとの比較 | QuTiP 5.2.3 との数値比較。収束次数の確認を含む | [制御モデル](../physics-model/validations/control-models.md) |
| 内部整合性 | CPTP性の全時刻監視、Rust実装とPython実装の一致 | [時間発展](../physics-model/validations/propagation.md) |
| 実機との比較 | IBM Quantum の実機へジョブを投入し、観測量を比較 | [実機比較](../physics-model/validations/hardware-comparison.md) |

:::info[合わなかった結果も公開しています]
実機比較は**形式的な合格判定に至っていません**。$T_1$ 緩和のフィット値はモデル参照値より一貫して大きく、Ramsey系列は比較時のモデルが実機側の微弱な離調を持たなかったため大きくずれました。現在はシミュレーション内解析として一定離調を指定できるRamsey専用スイープを追加していますが、保存済み実機比較の結果は更新していません。カバー率も事前に定めた基準の90%に届いていません。主因と切り分けた読み出し誤差はその後モデルへ実装しましたが([読み出し誤差の検証](../physics-model/validations/readout-error.md))、実機での効果確認は未実施です。ジョブID・生データ・再解析スクリプトを含む詳細は[実機比較](../physics-model/validations/hardware-comparison.md)にそのまま記載しています。
:::
