## 0. はじめに — 量子コンピュータと、この文章に出てくる言葉

以降の説明で使う用語を、先に簡単に整理させてください。

### 0-1. なぜ量子コンピュータなのか

いまのコンピュータは、情報を 0 か 1 の**ビット**で扱います。8ビットあれば、256通りの状態のうち「どれか1つ」を表せます。

量子コンピュータが使う**量子ビット（qubit）**は、0 と 1 の**両方が重なった状態**を取れます。8量子ビットあれば、256通りすべてを同時に抱えたまま計算を進められます。量子ビットを1個増やすたびに、扱える状態は2倍になります。

ただし、最後に測定すると答えは1つに決まってしまいます。そこで、**正解の確率だけが大きくなるように波を干渉させる**——これが量子アルゴリズムの考え方です。この文章に出てくる**Grover探索**は、その代表例で、大量の候補から目的のものを探す手順です。

うまく使えば、いまのコンピュータでは現実的な時間で解けない問題——新しい薬や材料の設計、暗号、大規模な最適化——に手が届くと期待されています。

### 0-2. 量子回路と、そこで使う言葉

量子コンピュータへの命令は、**量子回路**という図の形で書きます。横線が量子ビット、その上に並ぶ四角が**量子ゲート**です。

- **量子ゲート**：量子ビットの状態を変える操作。`X`（0と1を反転させる）、`H`（重ね合わせを作る）などがあります。
- **測定**：最後に量子ビットを読み出す操作。ここで重ね合わせが壊れ、0か1に確定します。
- **量子状態**：量子ビットが「いまどうなっているか」。本文の**密度行列**は、ノイズで濁った状態まで含めて表せる、その書き方の一つです。

### 0-3. 現実の装置で起きること

ここまでは理想の話です。実際の装置では、次のことが起きます。

- **デコヒーレンス（状態が崩れる）**：量子ビットは環境から熱や電磁的な揺らぎを受け、時間とともに情報を失います。その持ち時間の目安が **T1・T2** で、単位はマイクロ秒（μs、100万分の1秒）です。
- **制御パルス**：実機に「Xゲート」という部品はありません。**超伝導量子コンピュータ**では、量子ビットにマイクロ波を短く当てることでゲートを実現します。この波形が制御パルスで、**DRAG** はその波形を工夫する代表的な手法です。
- **リーケージ（漏れ）**：量子ビットは本当は 0 と 1 だけの入れ物ではなく、その先に使わない第3準位（|2⟩）を持っています。パルスが乱暴だと、確率がそこへ漏れ出して計算が壊れます。

### 0-4. 本文に出てくる、その他の言葉

以降、物理モデルと検証の話で次の言葉が出てきます。読み飛ばしても筋は追えますが、気になったときに戻ってきてください。

**状態と、その良し悪しを測る言葉**

- **時間発展**：量子状態が時間とともに変わっていくこと。その変化を計算するのがシミュレーターの仕事です。
- **Fidelity（忠実度）**：理想の状態にどれだけ近いか。1 が「完全に理想どおり」で、崩れるほど下がります。
- **Purity（純度）**：状態がどれだけ「濁っていない」か。1 が澄んだ状態で、環境と混ざるほど下がります。
- **開放量子系**：まわりの環境と熱や情報をやりとりしている量子系のこと。現実の量子ビットはすべてこれです。
- **散逸／熱励起／位相緩和**：崩れ方の種類です。散逸はエネルギーを失って 1 から 0 へ落ちること、熱励起はその逆に温度で 0 から 1 へ上がること、位相緩和は 0 と 1 の「波のタイミング」だけがずれて重ね合わせが失われることを指します。

**計算のしくみに関わる言葉**

- **ハミルトニアン**：その系のエネルギーを表す行列で、状態がどう変化するかを決めるもの。「装置の設計図」にあたります。
- **崩壊演算子／緩和レート**：環境による崩れ方を数式で表したものと、その速さ。**Lindblad方程式**は、この崩れまで含めて時間発展を書く標準的な方程式です。
- **ソルバー**：その方程式を数値的に解くプログラム。本文の**RK4（4次のルンゲ・クッタ法）**は、時間を細かく刻んで少しずつ進める代表的な解法です。刻みを細かくするほど誤差が減る速さを**収束次数**と呼びます。
- **CPTP性**：計算結果が「確率として成り立っているか」の条件。確率の合計が1のままか、負の確率が出ていないか、ということです。これが崩れていたら、計算のどこかが間違っています。

**超伝導量子コンピュータまわりの言葉**

- **トランズモン**：いま主流の超伝導量子ビットの方式。本文の「トランズモン数」は、シミュレートする量子ビットの個数です。
- **非調和性**：0→1 と 1→2 で必要なエネルギーの差。これがあるおかげで 0 と 1 だけを狙って操作できます。小さいほどリーケージが起きやすくなります。
- **離調（detuning）**：かけたマイクロ波の周波数と、量子ビットの周波数とのズレ。
- **磁束ノイズ**：超伝導回路を貫く磁場のゆらぎ。位相緩和の原因になります。
- **読み出し誤差**：測定装置が「0 を 1 と読む」「1 を 0 と読む」間違い。量子状態そのものの崩れとは別物で、本文4-3節の主題です。
- **キャリブレーション（校正）**：実機が定期的に測り直している T1・T2 などの実測値。実機比較では、これを入力として使いました。

**検証の話に出てくる言葉**

- **QuTiP**：量子系の計算に広く使われている研究用のPythonライブラリ。本文では、自作の計算が正しいかを確かめる「答え合わせ相手」として使っています。
- **Ramsey系列**：位相緩和（T2）を測るための定番のパルス手順。重ね合わせを作って少し待ち、位相がどれだけずれたかを読み取ります。
- **事前登録**：測定を始める前に「何をもって合格とするか」を決めて記録しておくこと。結果を見てから基準を作らないための手続きです。
- **ブートストラップ信頼区間**：測定データから統計的に見積もった「このくらいの幅には収まるはず」という範囲。

Yuragi-Striderは、この「理想の量子回路」から「現実の装置で起きること」までを、同じ画面の中でつないで見せるツールです。

## 1. このシミュレーターでできること

Yuragi-Striderは、**量子コンピュータが「理論上どう動くか」だけでなく、「現実の環境ではどう崩れ、実機ではどう動かされるのか」まで追える量子回路シミュレーター**です。

- 量子回路を視覚的に組み立てて、その動きを見る
- 温度やノイズを変え、量子状態が崩れていく様子を見る
- Grover探索などの量子アルゴリズムが、現実的な環境ではどのように効果を失っていくかを見る
- ゲートの実行時間まで考慮してシミュレーションする
- さらに一段下の、超伝導量子コンピュータを動かす制御パルスから設計・シミュレーションする
- 分からない理論は、公式ドキュメントからそのまま学ぶ

「量子回路を動かす」だけではなく、

**アルゴリズム → ゲート → ノイズと時間 → 物理的な制御**

まで、一段ずつ実際の量子コンピュータへ降りていけることを目指しました。

## 2. なぜ作ったのか

### 2-1. 数式の向こう側を、自分の手で確かめたかった

量子力学や量子情報を勉強していると、量子状態、量子ゲート、密度行列、時間発展など、さまざまな数式が登場します。

しかし、勉強を進めるうちに一つの疑問が生まれました。

**「この計算は、実際の量子コンピュータではどういう現象として起きているのだろう？」**

教科書では、XゲートやHゲートを作用させれば、量子状態は数式通りに変化します。

しかし実際の量子コンピュータでは、計算している間にも時間が流れています。量子ビットは周囲の環境と相互作用し、ノイズや散逸の影響を受けます。より分かりやすく言うなら、温度や磁場の影響を受けます。

さらに、実機には「Xゲート」という物体が存在しているわけではありません。超伝導量子コンピュータでは、マイクロ波などの制御信号を量子ビットへ与えることによって、量子ゲートに相当する操作を実現します。

つまり、教科書で見ていた量子回路と、実際の量子コンピュータの間には、まだいくつもの層がありました。

そこで私は、**量子アルゴリズムを動かすところから、環境による劣化、さらに実機の制御に近いところまで、自分で一つずつ降りて確かめられるシミュレーターを作りたい**と考えました。それがYuragi-Striderの出発点です。

## 3. Yuragi-Striderの新規性

### 3-1. 既存ツールとの位置づけ

量子シミュレーションの技術そのものは、すでに非常に発達しています。まず、Yuragi-Striderが使っている物理モデル——Lindblad型の開放系時間発展、CPTP写像、回転波近似下の駆動トランズモンモデル——は、**いずれも量子光学・量子情報の分野で確立された既知のもの**です。私が新しい物理法則を作ったわけではありません。

私が感じた課題は、**それらへ到達する経路**にありました。初心者向けの量子回路シミュレーターは「Hゲートを置く」「測定する」という分かりやすい抽象化で止まります。一方、ノイズ・開放量子系・制御パルスまで踏み込もうとすると、数式とコードを直接扱う研究用ライブラリの世界へ一気に移ります。その間に、なだらかな坂がありません。

既存ツールを「学習者がどの層まで到達できるか」という観点で並べると、その空白がはっきりします。

### 3-2. 「QuTiPを再現してGUIで包んだのではないのか」について

ここで、誤解されやすい点を先に書いておきます。**「既存ライブラリをGUIでラップし、同じ計算を再現しただけではないか」**という見方です。

これに対しては、Yuragi-Striderが大事にしている3つの価値——**反復性と解釈容易性・実機レイヤーの連続的な体験・徹底的な検証**——と、そもそもの入力の違いという、4つの点から答えられます。

**1. 何度でも目で見て確かめられること**——この時間発展の計算は、QuTiPを呼び出しているのではありません。Lindblad方程式のソルバーを自分で実装し、高速化のためのRust実装まで書いています。計算そのものが自作です。そして自作にした理由は、速度だけではありません。既存ライブラリのソルバーは「最終状態を正しく返すこと」に最適化されていますが、このアプリが見せたいのは**途中経過そのもの**です。各時刻の密度行列・Fidelity・Purity・確率分布を揃った形で取り出し、ゲート列の境界や測定の瞬間に印を付け、複数のグラフが同じ物理時刻を指したまま動く——そのための出力を、ソルバーの側から設計しました（4-4節）。可視化に最適化された計算基盤である、ということです。

**2. 実機を設計するレベルまで降りられること（後述のPulseモード）**——QuTiPやQiskit Dynamicsでもパルス計算はできます。しかしそれは、ハミルトニアンを式で書き、コードでソルバーを呼ぶ世界です。Yuragi-Striderがやったのは、**その層をGUIの操作対象に翻訳したこと**でした。波形パラメータをどう画面上の操作に落とし、変えた結果としてリーケージがどう動くかを、コードを書かない人にその場で見せる。この設計は既存ライブラリのどこにも存在しないので、再現しようがありません。

**3. 検証のためにこそQuTiPを使っていること**——ここでのQuTiPは**答え合わせ専用**であり、本番計算からは完全に切り離しています。むしろ話は逆で、自作したからこそ独立ライブラリとの突き合わせに意味があります。QuTiPを呼んでいるなら、QuTiPと一致するのは当たり前で、検証にはなりません。さらに収束次数、CPTP性、Rust/Python間の一致、そして**IBM Quantum実機との比較**まで行っているのは、ライブラリの利用者ではなく実装者の立場だからです。

**4. そもそも入力する量が違う**——QuTiPやQiskit Dynamicsに与えるのは、ハミルトニアンと崩壊演算子、つまり**すでに物理から数式へ翻訳し終えた量**です。緩和レート γ↓・γ↑（どのくらいの速度で量子状態が壊れていくか）を自分で計算して渡す必要があります。Yuragi-Striderが受け取るのは、**温度[mK]、磁束ノイズ[Φ₀]、量子ビット周波数[GHz]といった、装置の側の量**です。たとえば「なぜ超伝導方式では冷凍機が重要なのか、温度が高いとどうなってしまうのか」を直接問えます。この**物理量からレートへの変換モデル自体が独自の実装**であり、既存ライブラリには存在しない層です。

![](/pic/b9de7466-f00e-48a4-816d-83860601f105.png)

そして、この変換層も検証対象にしています。温度と量子ビット周波数から実装が構成する上向き・下向きのレート比が、独立に書き下したBoltzmann因子と **5.6×10⁻¹⁷**（倍精度の丸め誤差そのものの水準）で一致すること、さらに時間発展させた平衡状態がGibbs分布から求めた値とやはり **5.6×10⁻¹⁷** で一致することを確認しました。UIの入力欄を物理量に置き換えただけでなく、その変換が熱力学的に正しいことまで裏づけています。

まとめると、既知の物理モデルを使っている点はその通りですが、**計算は可視化に最適化して自作し、物理量を入力に取る変換層は独自で、GUIへの翻訳は前例がなく、検証はその全体を裏づけるために行っています**。

### 3-3. Gate-awareモード：アルゴリズムと現実環境をつなぐ

一般的な量子回路シミュレーターでは、量子ゲートは瞬間的な操作として扱われます。Yuragi-StriderのGate-awareモードでは、そこに**「ゲートを実行するにも時間がかかる」**という考えを加えました。計算している時間にも、量子ビットは環境（温度や磁場など）の影響を受け続けます。そのため、理想的な回路ではきれいに動く量子アルゴリズムでも、現実的な環境では結果が変わります。

例えばGrover探索と呼ばれるアルゴリズムでは、量子干渉によって探索対象の状態を見つける確率を高めます。Yuragi-Striderでは、その高められた確率が、**ノイズや散逸を含む環境の中で時間とともに崩れていく様子**まで観察できます。つまり、「Grover探索が動いた」で終わるのではなく、「その効果は現実的な環境の中で、どれくらい保たれるのか」まで見ることができます。

### 3-4. Pulseモード：さらに実機側へ降りる

Gate-awareモードよりさらに低いレイヤーを扱うために、**超伝導量子コンピュータを想定したパルス式シミュレーションモード**も実装しました。
次の写真は、実際に回路を波形レベルで調節しながら設計している例です。(3-4-1とは無関係)

![](/pic/121246bb-fb78-4873-8c2c-b0db69df59a6.png)

量子回路上では、XゲートやHゲートは一つのブロックとして表示されます。しかし実際の超伝導量子コンピュータでは、量子ビットに制御パルスを加え、その物理的な時間発展によって量子状態を操作します。Pulseモードでは、完成したゲートを置くだけではなく、**「どのような制御を量子ビットへ加えるか」**という、よりハードウェアに近い視点からシミュレーションします。

ここでは、実機で問題になる現象も扱えます。超伝導量子ビットは本来2準位ではなく多準位系であり、強いパルスをかけると計算に使わない第3準位へ確率が漏れ出します（リーケージ）。Yuragi-Striderは3準位モデルとDRAGパルスを実装しており、**この漏れをパルス波形の設計によって抑えられることまで観察できます**。

#### 3-4-1. 実際に、パルス波形だけでリーケージを4割減らす

**DRAG係数 β = 0.002 のとき — リーケージ 6.32%**

![](/pic/cba099ba-9a96-4923-8d9b-8086ecb4ceb4.png)

同じ回路・同じ環境・同じ時刻で、**DRAG係数 β を 0.001 から 0.002 に変えただけ**です。それだけで、計算に使わない |2⟩ への漏れ（リーケージ）が **10.04% → 6.32%** と、およそ4割減りました。計算部分空間に残る確率は 89.96% → 93.68% に改善しています。

これは「パルスの波形設計そのものが、量子ゲートの質を決めている」ということを、GUI上で数値として確かめられたということです。回路図の上で「Xゲート」を置いているだけでは、この違いは決して見えません。

**測定条件**

| 項目 | 設定値 |
|---|---|
| 準位数 | 3準位 qutrit（漏れ準位あり） |
| トランズモン数 | 1 |
| 時間発展の解法 | 固定ステップ RK4 |
| 観測時間 | 0.04 μs（スナップショット 104点） |
| 非調和性 | −100 MHz |
| パルス列 | X/2 → Y/2（各 0.0160 μs） |
| 波形 | Gaussian（σ = 0.002 μs、打ち切り 4σ） |
| 回転角 | π/2 rad（位相 0、離調 0） |
| **DRAG係数 β** | **0.001 / 0.002（この2つだけを変更）** |
| 温度 | 50 mK |
| デバイス品質 | 0.8 |
| 磁束ノイズ | 1×10⁻⁶ Φ₀ |
| 量子ビット周波数 | 5 GHz |
| 最大 T1 / Tφ | 100 μs / 100 μs |
| 準静的離調ノイズ | 無効 |
| デバイスプロファイル | 教育用デフォルト（実機校正値ではありません） |

比較しているのは、駆動中の同一時刻 0.0257 μs のスナップショット（純度はそれぞれ 0.999158 / 0.999248）における密度行列の対角成分です。リーケージは駆動中も時間とともに変動するため、βの効果だけを取り出せるよう、比較する時刻を揃えています。Pulseモードでは測定を回路の一部として扱わないため、これは射影測定の結果ではなく、その時刻の量子状態そのものを見ています。

**量子アルゴリズム → 量子ゲート → ゲート時間と環境ノイズ → 量子状態の時間発展 → 実機を動かす制御パルス**

という異なるレイヤーを、一つの環境の中でつなげて見ることができます。

## 4. 作るうえで苦労したこと・こだわったこと

### 4-1. 「動く」だけでは、シミュレーターとして足りない

最も苦労したのは、**「表示された結果を、本当に信じてよいのか」**を確認することでした。

量子力学のシミュレーションでは、プログラムがエラーを出さず、きれいなグラフが表示されたとしても、それだけでは正しい計算とは限りません。そこで、時間発展、散逸、位相緩和、測定などについて文献を調べ、実装する物理モデルを一つずつ整理し、次の4つの方法で検証しました。結果はすべて機械可読な形で `validation_results/` に残しています。

![](/pic/7ee44120-87e1-4376-a802-3521f54c42e8.png)

**1. 独立ライブラリとの比較**

独立ライブラリ QuTiP を本番計算からは完全に切り離し、答え合わせ専用として使いました。同一の初期状態 ρ(0)、ハミルトニアン H(t)、崩壊演算子を両方のソルバーへ渡し、出てきた量子状態を突き合わせます。

![](/pic/a4cbac1e-60b6-4d05-9840-80f3258b86de.png)

散逸・熱励起・純位相緩和を含む駆動2準位パルスで、両者の最大要素誤差は **6.6×10⁻⁸** 以下に収まりました。実行前に合格判定のしきい値として設けた 5×10⁻⁷ を、一桁近く下回っています。2〜4個のトランズモンを交換結合でつないだネットワーク系でも、同じ方法で最大要素誤差 **2.1×10⁻⁵**（固定ステップRK4経路）を確認しました。この結合ネットワークの比較では、QuTiP側が公開APIのリクエストJSONだけを読んでハミルトニアン・崩壊演算子・包絡線を独立に組み直しており、積分器だけでなく行列構成の誤りまで検出できる設計にしています。

**2. 数値解法の収束次数の確認**

時間刻みを1/2にするごとに、誤差がおよそ **1/16 ずつ** 小さくなることを確認しました（観測された収束次数は 4.02〜4.09、理論値は 4）。これは数値解法（4次のルンゲ・クッタ法）が理論どおりの精度で収束していることを意味します。「たまたま合っていた」のではなく、正しい理由で正しい答えに近づいていることの確認です。

**3. 物理的な妥当性の常時監視**

密度行列のトレースが1に保たれているか、固有値が負にならないか（CPTP性）を全時刻で検査しています。また高速化用のRust実装とPython実装を突き合わせ、差が **10⁻¹⁵**——倍精度浮動小数点数の限界——であることを確認しました。

**4. 実機との比較**

そして最後に、**IBM Quantumの実機（ibm_kingston）へ実際にジョブを投入し、私のモデルの予測と突き合わせました。** これは「候補段階」の探索的な比較であり、事前登録したプロトコルに基づく形式的な合格判定にはまだ到達していません。以下では、合った部分も合わなかった部分も、そのまま書きます。

実機から取得したキャリブレーション値（T1 = 303 μs、T2 = 340 μs）をそのまま入力として与え、遅延時間を0〜400 μsまで変えながら、IBMのネイティブゲートでモデル上の回路を実際に時間発展させ、測定した励起状態の残存確率を実機と直接比較しました。
より簡潔に表現するなら、"量子ビットの壊れ方"がどれくらい同じかを見たイメージです。



**T1緩和（振幅が減っていく過程）** については、差は平均 **5.9%**、最大 **10.8%** でした。一方で **位相緩和を見るRamsey系列** は、実機に見えた微弱な振動（数kHzの離調）をモデルが持っていないため、大きくずれました（平均差 約29%）。
注意点として、これは単一の実機についての、単一のジョブを中心とした検証です。

### 4-2. 合わなかったところも、そのまま書く

この比較では、**合わなかった点も、なぜ合わないかも記録しています。**

**1. 形式的な合格には至っていない。** 測定前に「計画した遅延点の90%以上がブートストラップ信頼区間に入ること」を合格基準に定めていましたが、実際のカバー率はT1で14.3%、T2で57.1%でした。原因は手続き上の理由（プロトコルの事前登録が実行前に完全には確定していなかった）と統計上の理由（カバー率不足）の両方です。

**2. T1のフィット値がモデルより一貫して大きい。** 実行ごとに 360／392／410 μs とばらつき、いずれもモデル参照値（約300 μs）を上回りました。上のグラフでも、遅延時間が長くなるほど実測点がモデル曲線から上へ離れていきます。実機の測定値がモデルより高く出ており、この比較を行った時点で**読み出し誤差（readout error）をモデル化していなかった**ことが主な要因だと考えています。実際、読み出しの較正データでも約0.7%の誤差が観測されていました。

**3. 「古い校正値のせいでは」という仮説も自分で潰しました。** モデル参照値を新しい校正スナップショットに差し替えて再解析しましたが、カバー率は改善せず（T2はむしろ悪化）、不一致は校正ドリフトでは説明できないと分かりました。

シミュレーターにとって大切なのは、都合のよい一致だけを見せることではないと考えました。**何が合っていて、何がまだ実装されていないのかを明示すること**も、物理シミュレーターの誠実さだと思います。ジョブID、キャリブレーション取得時刻、生データ、再解析スクリプトはすべて公開しており、同じ検証を再現できます。

### 4-3. 原因だと考えた要素を、実際に実装した

そして、上の「4-2」で主因と推定した**読み出し誤差を、その後モデルに実装しました。**

実機の測定は、量子ビットの状態を直接見るのではなく、共振器に電波を通してその変化を読む間接的なものです。そのため「0 なのに 1 と読む」「1 なのに 0 と読む」誤りが一定の確率で起きます。この誤りを、2つの校正値で表す混同行列としてモデルへ組み込みました。

実装で一番気をつけたのは、**どこに適用するか**でした。回路の途中にある測定は「重ね合わせを壊す」という装置内部の物理現象で、読み出し装置の判別ミスとは別のものです。そこで次のように分けました。

| 対象 | 読み出し誤差を適用するか |
|---|---|
| 出力確率・測定カウント | **する** |
| 密度行列・Fidelity・Purity | **しない** |
| 回路途中の測定による射影 | **しない** |

読み出し誤差は「観測装置の性質」であって「量子状態の性質」ではないからです。この分離が守られているかも検証項目にしました。実際、読み出し誤差を有効にしても Fidelity と Purity のズレは **厳密に 0.0**（1ビットも変化していない）で、一方で観測確率はきちんと約1.1%変化しています。

が、この読み出しモデルを入れたことで実機との一致が実際に改善するかは、**まだ確かめられていません。** 確認するには実機へもう一度ジョブを投入する必要がありますが、IBM Quantumの無料枠を先の検証で使い切っており、次の機会に持ち越しています。

次の方針としては 合格基準を測定前に凍結したうえで、`ibm_kingston` に加えて `ibm_fez`・`ibm_marrakesh` の3台の実機へ投入し、モデルとのズレが実機ごとにどう分布するかまで見ます。「実機ごとに崩れ方が違う」ということ自体を確かめたいからです。

現状は、「原因を考察し、対策を実装し、その数値的な正しさは検証した。実機での効果確認は次の機会へ」という状態です。上に載せた実機比較の結果は、この読み出しモデルを実装する**前**のものです。

### 4-4. 「いつ」の値なのかが分かるようにする

シミュレーターが数字を1つ返してきたとき、それが**回路のどの時点の値なのか**が分からないと、読みようがありません。Fidelity（1を理想的な状態として、そこからどれだけ壊れているかを見る指標）が0.87と出ても、それがゲートを全部かけ終わった後なのか、途中の待機時間中なのかで意味がまったく違います。

そこで、結果を**時間の流れに沿った列**として返すようにしました。各時刻について、量子状態そのもの（密度行列）、有効性（Fidelity）、安定性（Purity）、そして各状態の確率が揃って並びます。画面上のカーソルを動かすと、複数のグラフが**同じ物理時刻を指したまま**一緒に動きます。

さらに、時間を等間隔で刻むだけでなく、**回路の構造上の切れ目**にも印を付けています。

| 印の種類 | 意味 |
|---|---|
| 各ゲート列の境界 | その列のゲートを実行し終えた瞬間 |
| 測定 | 測定によって重ね合わせが壊れた瞬間 |
| 回路の終わり | すべてのゲートを実行し終えた瞬間（そこから先は待機） |

この印があると、「Hゲートを置いた直後に重ね合わせができて、CNOTでもつれて、そのあと待っている間にだんだん濁っていく」という流れを、**グラフの上でそのまま追える**ようになります。

見たい時刻を自分で指定することもできます。「0.5 μsのところだけ細かく見たい」といった調べ方ができるようにするためです。

### 4-5. 保存した結果を、比較できるときだけ比較する

条件を変えて試すツールである以上、**前の結果と今の結果を重ねて見たい**のは自然な要求です。実行結果は設定ごとファイルに保存でき、画面上でも1件を「保持」して次の実行と並べられるようにしました。

ただしここで、**なんでも重ねられるようにはしませんでした。**

重ねて意味があるのは、**比べたい条件以外がすべて同じとき**だけだからです。回路を書き換えてしまえば、グラフの差が「環境を変えたせい」なのか「回路を変えたせい」なのか分けられません。時間の刻み方が違えば、そもそも同じ物理時刻で並べることすらできません。



次の3つが一致している場合にかぎり「比較可能」と定義しました。

![](/pic/c8ae4df1-931f-4abf-b21d-031debb65832.png)

| 条件 | なぜ必要か |
|---|---|
| **回路が同じ** | 差が環境由来なのか回路由来なのか分けられなくなる |
| **観測する時間の窓が同じ**（全体の長さと刻み数） | 時間軸が違うと、同じ物理時刻で並べられない |
| **入力の与え方が同じ**（正規化パラメータか、物理量か） | そもそも同じ実験ではなくなる |

つまり**「環境パラメータだけを変えた実行」**が、比較してよい唯一の形です。

条件を変えて何度も試すことがこのツールの中心なので、その「変えた結果の見比べ」が正しく読める形になっているかどうかは、機能の数より大事だと考えました。

もう一つの苦労は、**「物理的に詳しくするほど操作が難しくなる」**という問題でした。情報を増やしすぎれば、初めて触ったときにとっつきにくくなります。しかし簡略化しすぎれば、実際の物理から離れてしまい、このシミュレーターを作った意味がなくなります。

物理的に深いところまで踏み込めることと、初めて開いた人が使えることは、両立させなければ意味がないと考えました。そのため、入口の側も同じだけ作り込んでいます。

## 6. これから

直近の課題は、実装した読み出しモデルを使って**実機比較をやり直すこと**です。合格基準を測定前に凍結し、複数のバックエンドへ投入して、モデルとのズレが実機ごとにどう分布するかまで見たいと考えています。特定の1台を再現できたとしても、別の実機ではまたズレるはずで、そのズレ方の分布こそが本来見るべきものだと思うからです。

あわせて、読み出し過程そのものの物理的なモデル化（共振器を含めた測定の時間発展）、扱える量子ビット数の拡張、より実機に近い制御モデルの追加を進め、教育用のシミュレーターとしてだけでなく、**量子デバイスや開放量子系について自分自身が研究するときにも使える環境**へ発展させたいと考えています。

### 6-1. 観測を「道具箱」にする

現在は、各時刻について密度行列と、そこから導かれる指標（各準位の占有確率、漏れ出し確率、純度）を一括で計算して返しています。しかし実際の実験では、「何を測るか」を実験者が先に決めます。

そこで、観測したい物理量をあらかじめ選んでから走らせる仕組みへ移そうと考えています。基本の指標に加えて、σz期待値のような、量子系を扱ったことがある人ほど見たくなる量も選べるようにしたい。密度行列そのものは既に保持しているので、そこから期待値を取る計算は今の基盤の延長で素直に載ります。

そして、必要な量だけを計算するようになれば、そのぶん一回の実行は軽くなります。より多くの量子ビット、より長い時間発展といった、これまで計算時間の面で扱いにくかった条件にも手が届くようになるはずです。**見たいところだけを、見たい形で観測する**——実験としての自然さと、扱える範囲の広さを、同時に取りに行きたいと考えています。

### 6-2. シミュレーターだけで終わらせない

Yuragi-Striderでは**公式ドキュメント**も整備しています。画面に登場する量子状態、密度行列、散逸、ノイズ、時間発展などについて、**「これは何なのか」「なぜこの計算をするのか」「このパラメータを変えると、物理的には何が変わるのか」**まで確認できる資料を目指しています。

シミュレーターで現象を見て、疑問が生まれたらドキュメントへ行く。理論を理解したら、条件を変えてもう一度実験する。**見る → 疑問を持つ → 理論を調べる → 試す**という循環そのものを、Yuragi-Striderという一つの環境をより大成させていこうと考えています

### 6-3. 攻撃シミュレーションモードの実装

前述のシミュレーション、検証基盤を生かし、研究論文などをもとに今後は量子コンピュータに対する攻撃シミュレーションモードを開発したいと思っており、このシミュレーターの価値をより分かりやすい形で主張していきたいと考えています。
