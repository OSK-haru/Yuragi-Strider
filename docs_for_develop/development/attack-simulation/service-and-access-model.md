# サービス差・攻撃者アクセス・課題成立条件

最終同期: 2026-09-28。設計段階の整理であり、API・スキーマ・採用サービスの確定仕様ではない。
ユーザーが明示した目的とサービス差への認識を基に、会話で提案した構造を記録する。
本書に挙げる操作や参照サービスを、すべて実装することを決めたわけではない。

## 1. 現在の中心思想

**共通化するのは全サービスで同じ攻撃ができることではなく、各サービスの条件と権限を表し、
その範囲で調査・操作・観測・評価できる仕組みである。**

装置に物理的な干渉が存在しても、サービスが必要な同時実行・操作・情報を提供しなければ、
特定の攻撃経路は成立しない。異なるサービスで個別に存在する能力を集めて、
一人の攻撃者が同時に持てる能力とみなしてはならない。

端末・コード編集・分析という共通体験と、課題ごとの接続先・操作権限・観測範囲を分ける。
物理モデルがパルスを扱うことと、攻撃者にパルス指定を許すことも別である。
攻撃者・被害者は同一service profile内で同じ主体非依存の操作catalogを使い、実効能力をservice能力、ActorPolicy、ScenarioPolicyの積集合として解決する。詳細は[共通操作・観測・校正契約](common-command-observation-contract.md)を参照。
疑似terminalは通常tenantのSDK／CLI／REST clientを表し、QPUや制御装置へのshell accessを表さない。
本節の権限は環境設定時の仮定として固定され、過程で変わるのはサービス状態から導かれる操作可能範囲だけで、攻撃者へ権限が与えられることはない。基盤の機能境界も仮定では変えない。詳細は[仮定・過程変化・不変の基盤](assumption-process-model.md)（D74）。

## 2. 攻撃目的・能力・成立機構の三軸

ユーザーが主要な目的として挙げたのは以下の三つ。表の順序は実装順や難易度順ではないが、最初の課題はReset越しに被害者の非公開出力bitを推定するO3型の情報漏洩へ固定した。

| 目的 | 保護対象 | 判定で区別する段階の案 |
| --- | --- | --- |
| O1 計算結果への干渉・改ざん | 被害者が受け取る結果の正しさ | 誤差増加、特定方向への偏り、狙った誤答・判断への誘導 |
| O2 アルゴリズム・回路・命令内容の推定 | 非公開の処理内容 | 候補の識別、構造・パラメータの推定、ゲート列や低レベル命令の復元 |
| O3 処理に埋め込まれた秘密の推定 | 非公開の入力・設定 | 秘密ビット、入力値、パラメータなど。業務上の価値を初期課題の必須条件にはしない |

攻撃目的と、Reset・クロストーク・Readout等の成立機構を一対一に固定しない。
各課題で「何を達成したいか」「何を操作・観測できるか」「何を介して影響するか」を組み合わせる。
O2とO3は回路に秘密が埋め込まれる場合に重なり得るが、保護対象と提出物は明示する。
O1では物理的干渉と返却JSONの直接編集を区別する。O3では秘密と観測をつなぐ因果が必要。

## 3. 上位設定で区別する五つの意味と設定境界

| 設定 | 主に決めるもの | 他の設定と混同しない点 |
| --- | --- | --- |
| 装置・物理 | 結合、緩和、駆動応答、Reset・Readoutの物理特性 | 物理効果があることは、その操作を利用者へ公開することではない |
| サービス | 公開命令、パルス受付、割当、時間共有／同時共有、Reset適用方針、公開情報 | 装置能力のすべてをAPIへ公開するとは限らない |
| 被害者 | 秘密・回路・反復・結果利用、サービスへの要求 | 専有を要求することと、サービスが保証することは別 |
| 攻撃者 | アカウント・役割・接続経路、許可操作、観測範囲、事前知識 | 管理者用の環境編集と、攻撃者として到達可能な操作は別 |
| 課題 | 背景、目的、三者とサービスの対応、予算、判定、根拠・追加仮定 | 物理的効果を成功フラグで代替しない |

五区分は意味上の責務であり、五画面・五部品・五つのトップレベルJSONを要求しない。
実装向けには、攻撃者→`AttackerConfig`、被害者→`VictimConfig`、装置・サービス→`QpuServiceConfig`へ対応させる。主体間の通信・配置・時間関係は`RelationConfig`、開始条件・training・対照は`ExperimentConfig`へ分け、`ScenarioPolicy`が編集・秘匿・提出を統制する。正式schemaは[仮定取扱契約](assumption-handling-contract.md)で提案中である。

共有方式を上位の被害者・利用環境設定から扱う既存方針は維持するが、被害者側が指定するのは希望する利用条件である。
実際の共有方式、割当、排他保証、Reset方針は`QpuServiceConfig`が所有し、被害者向け画面へ設定入口を置くことと内部状態の所有を混同しない。
具体的な画面配置、field、API schemaは未決定。

## 4. 攻撃側へ公開する操作の候補

ジョブ送信を、より広い「許可された操作要求」の一種として扱う案。
標的の接続先は課題ごとに異なり、すべての操作を同じQPU APIへ押し込まない。

| 能力候補 | 攻撃者が触るもの | 追加で必要となる条件 |
| --- | --- | --- |
| 回路の実行・測定 | 回路コード、待機・測定指定、自分のジョブ結果 | 対応命令、割当、実行方式、結果の公開契約 |
| パルスの実行 | 許可されたチャネルの波形・スケジュール | パルスAPIと、そのチャネル・周波数等の制限 |
| サービス利用操作 | 装置選択、状態照会、取消、予約等 | 提供される操作の種類と、それが時間・割当に及ぼす影響 |
| 物理サイドチャネルの観測 | 仮想計測器、電力等の時系列データ、解析コード | 計測経路へのアクセス。通常テナントに無条件で与えない |
| 利用部品の編集・提供 | 被害者が読み込む指定ファイルやカスタムゲート | 当該部品への変更権・供給経路と、被害者が採用する過程 |

自分の回路を使う攻撃、計測経路を持つ攻撃、被害者の依存部品へ介入する攻撃は異なるアクセス条件。
これらの採用範囲は未決定であり、現地侵入やソフトウェア侵害の手順まで実装することは決めない。
古典的準備を省略する場合も「どのアクセスを既に得ているか」を開始条件として記す。
許可された部品編集は攻撃側からの操作であり、上位設定の無制限編集を攻略手段にすることではない。

## 5. 観測・時間・結果を分離する

利用者へ返す観測には、本人の測定、service公開情報、そこからの利用者導出、simulator内部情報の別を持たせる。内部graderが相互情報量を算出できることを、攻撃者が同じ値をserviceから取得できる根拠にはしない。

| 情報 | 公開範囲の設計案 |
| --- | --- |
| 装置一覧・公開校正情報 | 選んだサービスが公開する範囲で提供する |
| 自分のジョブ状態・結果 | 自分の権限で取得する |
| 混雑度・キュー内位置 | サービスが対応する場合のみ提供する |
| 被害者のID・回路・割当・実行時刻・結果 | デフォルトでは直接公開しない。追加権限・公開経路・推定手段があれば個別に定義する |
| 密度行列・全体イベント履歴・判定用の正解 | 演習管理・判定・解説用。課題中の観測APIへ無条件に流さない |

区別すべきこと:

- キューが見えること／被害者を識別できること／被害者の実行時刻が分かること。
- 同じ装置を選ぶこと／同じ物理資源に割り当てられること／同時に実行されること。
- 重なる機会があること／実行時刻を知ること／開始時刻を自分で制御できること。
- 被害者に影響が生じること／攻撃者がその影響を確認できること／判定器が確認できること。

情報取得は、自分の測定、許可された計測データ、被害者アプリの公開出力などの経路ごとに定義する。
「被害者が結果を受け取り、その結果が攻撃者へ漏れる」を全課題共通の必須順序にはしない。
干渉が成功しても、攻撃者には提出前に成否が分からない課題も候補となる。

## 6. 課題の根拠を表示する案

以下は別の製品モードではなく、プリセットの説明・来歴の分類案である。

- **実サービス準拠**: 対象サービス・装置・プラン・確認時点と、再現した公開仕様を記録する。
- **研究上の構成**: 論文の版・節と、そこで仮定された同時共有・権限・知識等を記録する。
- **自由実験**: 任意条件で成立範囲を探る。現実のサービスに存在する組合せとは限らない。

一つのラベルだけで現実性を保証しない。条件ごとに、根拠と教育用の追加仮定を記録する。
「物理効果の実証」「その効果へ到達できる操作」「全能力が同時に成立する利用環境」を分ける。
実サービスの保証と矛盾する変更をした場合は、元サービス準拠の表示を維持しない案とする。

### 課題をレビューするときに残す情報（書式案）

1. 攻撃目的と達成の強さ（誤差増加なのか、指定結果への誘導なのか等）。
2. 装置、サービス、利用者の役割、接続経路。
3. 操作・観測・配置・時間に必要な能力と、それぞれの入手根拠。
4. 事前校正や訓練データを得る機会、被害者を識別する根拠。
5. すべての条件が同じ環境で同時に成立するか。成立しない場合は追加仮定を明示する。
6. 効果をなくす対照、提出判定、判定器だけが見える情報。
7. 参照元・版・確認日、実証範囲と未実証範囲。

## 7. 会話で調査した根拠と限界

以下は2026-09-19までの会話で読んだ一次資料の要約である。
今回の文書編集では新たな外部調査を行っていない。将来の現行仕様を保証する表ではない。
攻撃用コード・手順の実行や外部実機への接続は行っていない。

### QubitHammerから引き継ぐレビュー事項

論文が能力を「現実的」と呼んでいても、それを現在の全サービスの保証に置き換えない。
特にshotsの反復は、時間的重複の機会の議論であり、被害者時刻を知る手段の説明とは別である。
§IVの対象量子ビットの事前測定についても、いつ操作できたのか、後の割当をどう知るのか、
公開校正情報を使うのかを、課題側で明示する必要がある。

## 8. 未決定のまま残すこと

- 最初に再現するサービス条件・課題と、実装する操作能力の最小集合。
- サービスプロファイルの形式、権限判定、観測API、配置・時間・状態寿命の契約。
- 計測器アクセスや部品編集の課題を初期版へ含めるか。
- 根拠表示と、条件編集後の分類・提出資格の更新方法。

今の段階では、複数事業者の完全なエミュレーターや、すべての攻撃経路を実装しない。
共通フローを仮置きし、性質の違う課題例で不足を確かめてから、最小範囲を決める。
