本書は要求・構想の整理であり、確定アーキテクチャや実装仕様ではない。

実装状況は確認日を付した [progress.md](progress.md) を参照する。

## 0. 読み方と全体像

- **合意済み**: ユーザーが明示した目的・方針。実装済みという意味ではない。
- **提案**: 会話中に提示した具体化案。採用は未決定。
- **懸念**: 設計レビューで指摘したリスク。欠陥が実証済みという意味ではない。
- **未決定**: 選択・仕様・評価基準が必要な事項。

以下の8レイヤーは議論を分類するための見取り図である。
以前提示した「8つの責務候補」とは別であり、8画面・8モジュール・8プロセスを決定しない。
番号は検討の流れを示すもので、厳密なソフトウェア依存階層ではない。

| レイヤー | 中心となる問い | 現在の状態 |
| --- | --- | --- |
| L1 目的・対象範囲 | 何を体験し、何を学ぶ製品か | 中核目的は合意。対象者・初期範囲は未確定 |
| L2 ユーザー体験・操作階層 | 誰として、どこから何を操作するか | 二階層とプリセット方針は合意 |
| L3 脅威モデル・シナリオ | 何を守り、誰が何を破るか | 三つの主要目的を明示。能力の入手経路・一課題の成立条件は未確定 |
| L4 サービス・被害者 | 要求を受ける側と利用する側はどう振る舞うか | サービス別の公開機能・権限を区別。共通フロー案あり、契約は未確定 |
| L5 実行管理・状態・時間 | 世界がいつ進み、何が残るか | 必要性を認識。重要な意味論が未確定 |
| L6 制御・物理・観測 | 操作からどんな物理的影響と測定が生じるか | 基準版と分離した内部プリミティブを初期実装。シナリオ接続は未実装 |

## L1. 目的・対象範囲

### 合意済み

- 量子コンピューターを通したセキュリティインシデントを、利用者が攻撃側から体験する。
- 今回の対象は量子暗号以外。過去に例示したQKDの盗聴は現在の対象に含めない。
- 古典的ハッキングの習得・実行を必須にせず、量子コンピューター特有の攻撃や懸念を見せたい。
- U-22での体験も意識し、調査・操作・観測・達成が一本の筋として通るようにする。
- プロジェクト全体の中心価値は理解と見える因果関係。CTF形式はそのための手段であり、ゲーム化自体が目的ではない。
- 主要な攻撃目的は、計算結果への干渉・改ざん、アルゴリズム／回路／命令内容の推定、処理に埋め込まれた秘密の推定。

目的、攻撃者の能力、物理・運用上の成立機構は別軸として整理する。
誤差増加と指定誤答への誘導、候補回路の識別と任意命令列の復元は、同じ達成水準ではない。

### これまでの主な対象候補

共有超電導QPUでの不完全Reset、クロストーク、相関Readoutを、テナント間隔離の破れとして扱う。
これはユーザーが挙げた重要な目標の一つである。

NISQは製品全体の不変条件にしない。現行の最初の縦切りを`nisq_physical` profileとし、FTQCは論理層・QEC・decoderを含む別profileとして将来追加できる境界を保つ。

製品全体は共有QPUだけに限定しない。成立条件は、攻撃者から被害者へ届く設定で宣言された共有資源・経路があることとした。
共有QPU型は引き続き最初の実装対象であり、同一QPU・同一物理量子ビットを順次使うReset課題の条件は維持する。
別QPU間の経路を宣言できることと、その作用機構を実装・検証済みであることは異なる。
追加の文献調査では、制御装置の電力観測や被害者が使うパルス部品への変更も候補として挙がった。
これらの採用は未決定。すべてを同時共有QPU・通常テナントのジョブ操作へ無理に当てはめない。

### 未決定

対象利用者の事前知識、具体的な学習到達点、初期リリースの課題数・対象現象、
採用する追加経路の範囲と、各経路を提供するサービス設定・実装・検証条件。
大規模・高忠実度な研究基盤へ無制限に広げないことも必要。

## L2. ユーザー体験・操作階層

### 合意済みの構造

1. 上位の「攻撃シミュレーター設定」で実機側・被害者側の設定を行う。
2. CTF型プリセットには、攻撃者・被害者・実機側の設定を割り当てる。
3. 課題内では攻撃側画面のみを操作し、攻撃もそこから行う。
4. 独立した高機能な攻撃者環境を用意する。回路編集と送信ボタンだけでは不足する。
5. 共通基盤上で自由実験と課題形式をセッション方針として分け、課題設定・提出機能を載せる。別製品・別実行基盤にはしない。
6. 一直線に完走できる初回チュートリアルを用意する。

ここでの「実機側」は模擬する装置環境を指す。現物への接続は決定していない。
「自由」は課題中に被害者の秘密や装置条件を直接書き換えられることを意味しない。

### 共通フローの具体化（2026-09-19）

ユーザーが示した設定→攻撃側へ移動→操作→実行・観測→個別判定を基に、
[architecture.md](architecture.md) に共通体験フローを整理した。
手動設定とプリセットは同じ環境構成への入口であり、別ランタイムではない。
ジョブ送信を「許可された操作要求」の一種とし、追加経路の採否は課題ごとに決める案。
攻撃者が利用先装置を選ぶことと、上位設定で装置特性を書き換えることを区別する。
取得結果を分析して次の操作へ戻る反復を含み、被害者結果の攻撃者への自動転送は置かない。

### 提案と未決定

端末・エディタ・ファイル・SDK/CLI・分析ツールを共通装備にする案がある。
言語、利用可能ライブラリ、コマンド、実行方式は未確定。
上位設定へ戻ったときの停止・再開、環境編集後の提出資格、ヒントと解説の開示時期も未決定。

直近の懸念は、古典的な準備を省略するだけでなく、時刻・配置・操作まで全部与えると、
課題が「指示どおり実行して提出するだけ」になり得ること。
与える前提、調査して知ること、利用者が選ぶ操作を区別する必要がある。
チュートリアルでは手順を案内してよいが、その案内量を全課題の仕様にはしない。

## L3. 脅威モデル・シナリオ

### ユーザーの意図と具体化案

量子固有の現象へ集中するため、アカウント取得などの古典的準備を開始条件として与える案がある。
これは「現実の攻撃に古典的手法が不要」という主張ではない。
何を既に持っている想定なのかを明示し、どの前提を与えるかは課題ごとに決める。

正規クラウドテナントは攻撃者の一候補。計測経路や被害者の利用部品へのアクセスを持つ立場も候補として区別する。
手元PC、クラウド上の端末、現地端末という場所の違いだけでは能力は決まらない。
認証、公開情報、配置・時刻の指定権、利用可能な制御操作を定義する必要がある。

### シナリオでつなぐべき因果関係

共有QPUの測定に基づく情報取得では、次の経路を一つずつ説明する。

```text
保護対象の秘密
  → 被害者の量子ワークロードに反映
  → 共有資源を介した物理的依存
  → 攻撃者が取得できる自分の観測
  → 推定・提出
```

干渉では「攻撃者の許された操作 → 物理的影響 → 被害者結果への影響 → 被害判定」をつなぐ。
電力等の計測を採用する場合は、秘密に依存する制御信号→許可された計測経路→推定という別経路を定義する。
被害者が結果を受け取ってから攻撃者へ漏れる順序は、すべての課題の必須条件ではない。
被害の発生、攻撃者からの確認、判定器による評価を分離する。
サービスが返すJSONを直接書き換える仕組みとは区別する。
誤りを増やすことと、任意の望む値へ改ざんすることも区別する。

### 検討中の題材と前提

| 題材 | 必要となる関係 | 避けるべき飛躍 |
| --- | --- | --- |
| 不完全Resetによる残留の観測 | 被害者→初期化・待機→攻撃者という同一資源の再利用 | 一定の測定床があるだけで秘密が漏れるとする |
| 初期状態の汚染 | 攻撃者→初期化・待機→被害者という順序 | 残留の窃取と同じ時系列で説明する |
| 駆動クロストーク・ZZ | 適切な配置、実際の時間重複、操作・結合条件 | 同じクラウドを使うだけで同時駆動が成立するとする |
| 相関Readoutによる推定 | 他者状態に依存する観測と測定資源・時間関係 | 相関ノイズならどれでも情報漏洩になるとする |

これらは候補であり、既存商用サービスすべてで成立するとの主張ではない。
任意の被害者PC内のファイルは、量子ワークロードとの関係なしにQPU経由で読み出せる対象ではない。

### 未決定

最初の一課題、保護資産、サービスが本来保証する隔離、破られたとする基準、
攻撃者の初期知識と能力、被害者の秘密と回路の関係、攻撃のタイミングを知る手段。
各課題には「実サービスの根拠／研究上の仮定／教育上の簡略化」を分けて記録する案がある。
各能力が個別に実在しても、同じサービスで一人の攻撃者が同時に持てるとは限らない。
同じ装置の選択・同時実行・時刻の知識・開始制御を別の条件として評価する。

## L4. サービス・被害者と利用フロー

### 議論で整理した対応

| 利用フロー | 実環境で対応するもの | 模擬環境で表現する候補 |
| --- | --- | --- |
| コード・回路を作る | 利用者の端末、SDK | 攻撃者ワークスペース／被害者プログラム |
| 実行先に適合させる | 命令集合、接続関係、コンパイル | 対応命令と割当制約。変換処理の配置は未定 |
| 送信する | 認証API、ジョブ受付 | 利用者ID、自分のジョブID、受付・エラー |
| 待機・割当される | キュー、予約、スケジューラ | 時間共有・同時共有・専有の方針 |
| 実行される | 制御系、QPU、測定系 | 初期化・駆動・状態発展・測定 |
| 結果を利用する | 結果API、アプリケーション | 自分の測定結果と許可されたメタデータ |

サービス全体のジョブ並列処理と、チップ上での二者同時実行は区別する。
「running」表示だけで被害者の物理実行タイミングが分かるようにはしない。
提供する状態情報は、選ぶ参照サービスと脅威モデルに整合させる。

### サービス差を共通基盤へ反映する方向

ユーザーはサービス間で権限・設定・仮定の成立範囲が大きく異なると指摘した。
共通化するのは主体非依存の要求・結果形式と権限解決の仕組みであり、全サービスへ同じ能力を持たせることではない。同一service profile内では攻撃者・被害者が同じ操作catalogを使い、実効範囲を主体権限とScenarioPolicyで変える。serviceごとの能力差はServiceProfileで表す。
通常の回路受付、パルス対応、仮想計測、指定部品の編集は、課題条件に応じて区別する候補である。
UI・疑似ターミナル・被害者runnerは同じApplication APIのclientとすることで合意した。正式schemaとCLI構文は未決定。最初の縦切りは、同一物理量子ビットを順次再利用するReset越し漏洩に必要なjob送信・測定・結果取得だけを実装対象とする。

### 被害者の多様さを抑える提案

研究・最適化・その他の業務ごとに別システムを作るのではなく、
単発実行、固定反復、結果に応じた適応的実行という振る舞いから整理する案がある。
業務背景は、攻撃条件や被害判定へ影響しない限り説明文で表す。
ただし、背景を簡略化しても「何を守っているか」と「何が被害か」は省かない。

ジョブの入出力形式と、job/batch/sessionなどの実行管理方式は別軸として扱う。
初期版の被害者は、非公開出力bitを固定反復する単一量子ビットworkloadとする。適応実行や業務別workloadは後続に回す。

### 設定の責務候補

- 装置: 結合、緩和、駆動、Reset・Readoutの物理特性。
- サービス: 公開命令、パルス対応、共有方式、割当、Reset適用方針、公開情報。
- 被害者: 秘密入力、回路、反復や結果利用、利用先への要求。
- 攻撃者: 役割・接続経路、許可操作、観測範囲、事前知識。
- 課題設定: 上記の組合せ、目的、予算、説明、判定、根拠・追加仮定。

共有方式の設定入口を被害者側にまとめる方針と、内部データの所有者は別の話である。被害者は希望する利用条件を指定し、実際の共有方式・割当・保証はQPU serviceが所有する。
五区分は意味上の責務として維持し、主体が所有する値は攻撃者→`AttackerConfig`、被害者→`VictimConfig`、装置・サービス→`QpuServiceConfig`へ対応させる。主体間の通信・配置・時間関係は`RelationConfig`、開始条件・training・対照は`ExperimentConfig`へ分け、`ScenarioPolicy`は編集・秘匿・提出を統制する。
この責務分離は合意済みだが、画面数、モジュール数、正式field・永続化schemaは未決定である。

## L5. 実行管理・状態・時間

### 合意済みの検討必要性

時間・計算量・利用予算を明確に設計する。
仮想時間とPC上の実計算時間、演習予算とホスト保護の上限を分離する案がある。

### 直近で指摘した重要な懸念

既存の独立した回路実行を順番に呼ぶだけでは、ジョブをまたぐ物理履歴を表現できるとは限らない。
毎回初期化すれば残留が消え、逆に無条件に状態を持ち越せば不自然な漏洩を作る可能性がある。
必要なのは時計だけでなく、状態の所有者・寿命・更新規則の定義である。

| 対象 | 決めること |
| --- | --- |
| ジョブ終了後 | 量子状態、漏れ準位、古典的装置状態の何を保持するか |
| 待機中 | 緩和・位相変化・条件変動がどの時間で進むか |
| Reset時 | 誰がいつ適用し、どの状態をどのモデルで変えるか |
| ショット境界 | 再準備、Reset、秘密入力、持越しの単位 |
| 同時実行 | 二者を含む結合状態の管理と、イベントの順序 |
| 課題の再開始 | 物理状態、秘密、乱数、予算、ファイル、履歴のリセット範囲 |

被害者が利用者の操作待ちの間も進行するのか、ジョブ送信や明示操作で時間が進むのかも未決定。
攻撃者に仮想時刻を直接指定させる権限は、まだ与えると決めていない。

## L6. 制御・物理・観測

### 既存の土台と未実装の区別

物理モデルのみの基準版を先に固定する方針は実施済み。
基準は `699a110` / `yuragi-strider-physical-baseline-v1`。
基準版の土台に加え、2026-09-22に `core/experimental_isolation_physics/` を内部限定で追加した。

| 土台 | 攻撃モデルとしてまだ同一視できないもの |
| --- | --- |
| 量子ビット別T1・Tφ | ジョブ間ドリフト、継続する装置状態の管理 |
| 独立p10/p01 Readout | 他テナント状態に依存する相関Readout |
| 結合トランズモンと局所駆動 | テナント配置・同時実行管理、意図しない駆動クロストークの契約 |
| 交換結合、多準位状態 | 明示的な残留ZZ攻撃シナリオの完成 |
| 相関した準静的デチューニング | 相関Readoutやジョブ間の時間変動 |
| T1/Ramsey解析 | 攻撃成立や現行商用サービスでの再現性の証明 |

内部版 `shared_qpu_isolation_physics_v0` には、不完全ResetのCPTPチャネル、残留ZZのcross-Kerr項、疎な複素駆動伝達、局所クラスタ相関Readoutを実装した。公開API・UI、テナント状態、スケジューラ、課題判定にはまだ接続していない。したがって、物理機構の単体実装を攻撃シナリオの成立やサービス再現性の証明とは扱わない。

### 制御系をどこまで模擬するか

会話では「AWGのデジタル波形 → DAC・ミキサー・局部発振器 → QPU」という制御経路も論点になった。
現物の制御系全体を忠実に再現することは合意していない。
攻撃因果に必要な効果を有効パルスや結合係数で表すのか、装置応答を明示するのかは未決定。
モデル上の有効駆動を、実際の制御電子回路全体の再現と説明しない。
内部でパルスを計算することと、利用者へ任意のパルスを送信する権限を公開することは別。
過去の論文が使ったパルスアクセスを、現在の全サービスの標準機能として扱わない。

### 検証上の注意

過去の実機比較は一つの実機についての測定であり、他装置や条件への一般化には限界がある。
既存データとの整合、独立計算との一致、実機で攻撃が成立することは別々の主張である。
物理基準版の固定も、攻撃シナリオの妥当性を保証しない。
既存結果の数値や再解析は本書では更新しない。

## L7. 提出・検証・学習

### 合意済みと提案

CTFのflag提出に相当する達成判定を設けることは合意済み。
推定値、flag、ジョブID、スクリプトなど、何を提出するかは未決定。
判定後に達成証明としてflagを発行する案もあり、全課題で同じ方式にするとは決めていない。

CTFから共通化しやすいのは、作業環境、標的接続、課題定義、ヒント、提出、クリア記録。
本製品ではさらに、物理履歴、共有条件、被害者の進行、測定の確率性、対照条件を扱う必要がある。
これらが他のCTFに一切ない、という意味ではない。

### 分離して確認する四つの観点（提案）

| 観点 | 確かめること |
| --- | --- |
| 実装の検証 | 決めた仕様・権限・時間規則どおりに動くか |
| 物理・シナリオの妥当性 | 効果に根拠があり、想定した攻撃者の能力で因果経路が成立するか |
| 再現性 | 設定・モデル版・乱数条件・操作履歴を記録して追試できるか |
| 学習効果 | 利用者が成功条件だけでなく、原因・成立条件・限界を説明できるか |

同じseedで同じ結果になることだけでは、現実性の裏付けにはならない。
秘密を一度偶然当てることと、情報漏洩を示すことも同じではない。
必要に応じて複数ケース、未知ケース、効果を無効にした対照を使う案がある。
ただし、すべての提出課題に統計検定を要求するとは決めていない。

正常な隔離・十分なReset・結合なし等の条件で効果が消えるかを確認し、
特定操作を検出しただけで成功する仕組みとは区別する。
課題中の攻撃者向け観測と、終了後の全状態を使う解説も分ける必要がある。

実サービス準拠・研究上の構成・自由実験という来歴の表示案を追加した。
これは別製品モードではない。ラベルに加え、条件ごとの根拠・確認時点・追加仮定を残す。
現実のサービス仕様と矛盾する条件編集後も、元の準拠表示を維持する設計にはしない案。

## L8. 実装境界・品質・開発管理

### 8つの論理責務候補

以前の会話では次の分割を提示した。数・名称・境界はいずれも提案である。

| 候補 | 担当する仕事 | 主な関連レイヤー |
| --- | --- | --- |
| 攻撃者ワークスペース | コード、端末、ファイル、許可された接続先への操作、調査・分析 | L2 |
| 仮想QPUサービス窓口 | サービス条件に沿う認証、受付、状態照会、利用者別結果 | L3・L4 |
| 実行管理 | キュー、割当、時間、予算 | L5 |
| 物理エンジン | 初期化、駆動、結合、状態発展、測定 | L6 |
| 被害者ワークロード | 被害者の回路送信と結果利用 | L3・L4 |
| 実験・課題設定管理 | プリセット、環境構成、再開始 | L2・L5 |
| 提出・判定 | 提出物の評価、達成表示 | L7 |
| 記録・再生・解説 | 証跡、振り返り、チュートリアル | L7 |

UIの操作階層が決まったことは、API・データ所有・権限・プロセス境界が決まったことではない。
[architecture.md](architecture.md) の責務表・図もその具体化案として読む。
D57で実公開Webの状態・時刻・private判定はserver正本、編集・共通操作・許可された分析／表示はブラウザ側とした。server内部のprocess／container分割とSandbox後の攻撃者コード実行配置は未決定。[v1契約](common-foundation-v1-contract-proposal.md)を参照。
上表は主にジョブ経路の責務案。計測器や部品供給を採用する場合の配置・情報境界は別途設計する。

### 二種類の安全性を混ぜない

- 模擬する標的の安全性: テナント間の秘密・結果・操作権限をどう隔離するか。
- 製品自身の安全性: 利用者のコードからホスト、ファイル、ネットワーク、CPU・メモリをどう保護するか。

ローカル解析で正解を取り出せる点は教育用途として割り切る方針だが、
通常APIによる情報漏洩やホスト保護まで不要になるわけではない。
公開API、判定応答、ログ、解説機能による意図しない正解露出も検討対象になる。

### 開発プロセス上の現在地と不足項目

会話では現在地を、目的・範囲・利用シナリオ・前提条件を定める要求定義と、
初期アーキテクチャ検討として整理した。詳細設計の確定段階ではない。
ISO/IEC/IEEE 29148および15288の公開概要を参照した整理であり、規格本文の条項監査や適合宣言ではない。

不足する検討候補は次のとおり。

- 仮想の攻撃者・被害者とは別に、実際の学習者、課題作成者、説明者、保守者の要求を整理する。
- 対象者、学習目標、初期版の範囲、開発・配布・動作環境の制約を明文化する。
- 開始から提出までだけでなく、取消、失敗、予算切れ、中断、再開、設定変更を定義する。
- 「高機能」「軽量」「分かりやすい」を検証できる機能・品質条件へ具体化する。
- 外部接続、ファイル、保存、アクセシビリティ、停止・タイムアウトの契約を決める。
- 目的・要求・設計・実装・テストの対応と、設定・モデル・課題の版管理を残す。

これらをすべて詳細化してから試作するという合意ではない。
共通フローを仮置きし、課題例で不足を確かめて最小限の契約を具体化する案である。

## 10. 共通フローから課題例で検証する進め方（提案）

9月17日時点の「まず一課題を具体化する」という進め方を更新する。
共通フロー（誰が誰に何を渡すか）を先に仮置きし、サービスで固定する規則と課題で変える条件を分ける。
その後、性質の違う課題例を通して不足や矛盾を調べ、実行規則（時間・状態・権限）を具体化する。
共通構造だけで完結させるのでも、一課題に合わせてすべての構造を固定するのでもない。

課題例を検証する際は、以下を一組として埋める。
課題の選択や実装開始は、今回の文書化で承認されたものではない。

1. 保護対象と、本来守られるべき保証。
2. 被害者の振る舞いと、秘密・結果が量子処理へ関わる箇所。
3. 攻撃者に与える能力・情報・古典的準備の前提。
4. 利用者が調査・選択することと、使用する観測・ツール。
5. ジョブ・ショット・待機・Resetを通した状態の流れ。
6. 攻撃者の観測、被害者への影響、成立しない対照条件。
7. 提出物、達成判定、説明できることと主張できないこと。
8. サービス・装置・プラン・時点と、各能力の入手根拠・同時成立の確認。

詳細な未決定事項は [open-questions.md](open-questions.md)、
ユーザーの明示方針は [decisions.md](decisions.md) を参照する。
