# 同時共有の時間窓の設計案

最終同期: 2026-10-17。**提案が中心で、未承認の部分が多い。** 実装・schemaの確定ではない。
合意済み: 漏れは最初から**双方向**を対象にし、拡張性を優先する（2026-10-17、[D76](decisions.md)）。それ以外の項目は未承認。
[仮定・過程変化・不変の基盤](assumption-process-model.md)（D74）が定める「基盤は一般機能として一度だけ拡張する」の、その拡張の中身を書く。
クロストーク専用機能にはせず、「複数のジョブの窓が時間的に重なる実行」を一般の方針として加える。

## 1. 現状（コードで確認した範囲）

- ジョブの窓は`JobExecutionWindow`（到着・開始・終了・公開）で、`DeclaredServiceTiming.plan_job_window`が1ジョブずつ計画する。開始は「到着＋処理遅延」と「直前のジョブの終了の直後」の遅いほうで、窓は構造的に重ならない。
- 実行器`DeclaredQpuExecutor`は進行中のジョブを1つしか持たず、開始時に`window.start < _physical_end`なら`single-region physical windows overlap`で拒否する。開始を確定した時点で、そのジョブの物理計算を一括で用意（prepare）する。
- 状態は`QpuStateStore`が正本で、1つの稠密行列（アクティブ領域）とリビジョン列を持つ。別領域（`tenant_dedicated_region`）は`InactiveRegionState`として保持するだけで、同時には進めない。
- 駆動の窓は`TimeWindow`（半開区間）と`ScheduledDriveInterval`で別に表され、`select_active_drive_transfers`が実装・試験済み。ただし、どこからも呼ばれていない。
- 確定イベント列は`EventPosition`（時刻・同時刻順）の単調列で、`seal_ingress`が「この位置までの受付は出そろった」という透かしを与える。

## 2. 提案の全体像

同時共有を、サービスのアーキテクチャ仮定の新しい値として足す。既定は現行と同じ。

| 項目 | 内容 |
| --- | --- |
| 仮定の名前 | `scheduling.concurrency_policy` |
| 値 | `exclusive_fifo`（既定・現行）／`overlap_disjoint_regions`（新） |
| 成立条件 | `placement_policy = tenant_dedicated_region`。領域は互いに素で、各領域は別の状態を持つ |
| 固定の時点 | 環境設定時。成立後は変えない（D74） |

`overlap_disjoint_regions`では、別tenantのジョブが互いに素な領域で、時間的に重なって走れる。同じ領域を共有するジョブは、従来どおり重ならない。

## 3. 設計の柱

### 3.1 窓の型を一本にする

`ExecutionWindow`（提案）= ジョブID・tenant・領域の物理量子ビット・`EventPosition`の開始と終了・`DriveSchedule`。

- `DriveSchedule`は、コンパイル済み回路から決まる「どの量子ビットを、窓の開始からの相対時刻で、どの回転角・位相で駆動するか」の列。shotの構造（命令時間、Reset、shot間待機）は決定的なので、窓の開始時刻が決まれば確定する。
- `TimeWindow`は`EventPosition`の時刻から作る読み取り用の見え方にして、別の正本にしない。
- ジョブの4点（到着・開始・終了・公開）は従来どおり持つ。

### 3.2 重なりの決め方

- 計画時に、宣言済みの所要時間だけから決める。ホスト時刻は使わない。
- `exclusive_fifo`: 従来どおり、開始は直前の終了の直後まで押し出される。
- `overlap_disjoint_regions`: 領域ごとのFIFOにして、他の領域のジョブの終了を待たない。開始は「到着＋処理遅延」と、**同じ領域**の直前の終了の直後のうち遅いほう。
- 重なりは、窓の半開区間[開始, 終了)の交差で定義する。隣り合うだけ（`[0,1)`と`[1,2)`）は重ならない。

### 3.3 効果のモデル（双方向・拡張可能）

窓の重なりが生む影響を、三つの部品に分ける。同時共有の基盤が知るのは部品の形だけで、クロストークという個別の事象は知らない。

1. **活動記録（`ActivityInterval`）**: コンパイル済み回路から、窓の開始からの相対時刻で、量子ビットごとの活動を取り出す。種類は`drive`（回転角・位相）・`measure`・`reset`・`idle`。`DriveSchedule`はこの列の別名にとどめ、駆動以外の活動も同じ型に載せる。
2. **関係（`CouplingRelation`）**: 環境作成者が宣言する、領域をまたぐ影響の規則。関係の種類の名前、向き（source→target）、係数を持つ。種類ごとに、活動記録から`TimedEffect`の列を作る関数を登録する。今回実装するのは`drive_crosstalk`だけで、新しい種類を足すことが基盤の拡張になる。
3. **時刻付き効果（`TimedEffect`）**: 対象領域の状態へ、時刻順に適用する作用。種類は閉じた集合で、今回は`UnitaryKick`だけ。領域の実行器は、効果を時刻順に適用することしか知らない。

`drive_crosstalk`の具体:
- 環境作成者が`DriveCrosstalkTransfer`（複素係数）を向きつきで宣言する。**一方向でも双方向でも宣言できる**。双方向は、向きの違う2つの宣言で表す。攻撃者は選べない。
- source量子ビットの駆動が、相手の窓と重なる時間にあるとき、相手領域のtarget量子ビットへ「回転角＝|係数|×sourceの回転角、回転軸の位相＝係数の偏角＋sourceの位相」のキックを、その時刻に加える。`rz`は仮想で駆動なし。
- 双方向のとき、攻撃者の領域にも被害者の駆動のキックが入る。攻撃者の量子ビットが何もしない（`idle`）時間でも入るため、攻撃者は自分の量子ビットの変化から、被害者の駆動の存在や時機を読める。これが情報漏洩型の課題に使える経路になる。
- キックは「宣言された活動」だけから計算する。キックによって生じた活動が再び漏れる多段の経路は扱わない（第1近似）。
- 領域間は積状態のままにする。漏れは古典的な場による回転で、領域間のもつれは生じない。そのため2領域を同時に稠密に持つ必要がなく、各領域の状態は別々に進められる。
- 検証: 短い窓で、このキックが既存のパルスレベルの結合トランスモンのネットワークモデル（`core/pulse_transmon_network`）の結果と一致するかを比較試験にする。一致の許容は実測してから決める。

双方向でも循環依存は生じない。効果は、結果ではなく**活動記録**だけから計算される。サービスの回路は最後にまとめて測定する形だけを受け付け、測定結果に依存する条件分岐を持たないため、活動記録は測定結果に依存せず、窓の開始時刻が決まれば確定する。したがって、まず全ジョブの活動記録から全領域のキックを作り、次に各領域を独立に計算できる。**この性質は拡張時の不変条件**として扱う: 将来、途中測定や古典フィードバックを足すなら、活動記録が結果に依存するので、重なり群を時間刻みで同時に進める計算（共同シミュレーション）へ切り替える必要がある。

拡張の余地:
- `measure`・`reset`の活動を使う関係（読み出しの相関など）は、新しい関係の種類として足す（今回は実装しない）。
- **残留ZZ**は扱う（2026-10-17、[D77](decisions.md)）。ただし領域間にもつれを生み、積状態の仮定を破る。厳密な計算は2領域の合計12 qubitの稠密行列（4096×4096の複素数、約270 MB）となり、稠密計算の上限（8 qubit）を超えるため、計算量が爆発する。方針は段階とし、上の段階が計算量で成り立たなければ次へ進む: ①厳密に扱えるか（小さい構成で）を評価する → ②近似で扱う（例: 相手のZ基底の占有確率を重みとする、条件付き位相回転の混合。相手の状態が重ね合わせのときにもつれを無視する近似で、相手側の駆動が相手のZ占有を変える場合の誤差が出る）。近似の誤差は、小さな構成での厳密計算との比較で測る → ③それでも不可なら扱わない（宣言された係数があっても効果を生じさせず、その旨を根拠記録に残す）。
- 攻撃者が「待つ」ための**遅延命令**は、サービスの命令として追加した（§8）。

### 3.4 計算と確定の順序

現行は、開始確定の時点でジョブの物理計算を一括で用意する。重なる相手が後から到着しうるため、同時共有ではこれを変える。

- ジョブの物理計算は、そのジョブと重なり得る受付がそろった後（`seal_ingress`がそのジョブの終了位置を越えた後）に行う。
- 重なるジョブ群を一つの「重なり群」として一緒に計算する。結果の公開は群の最後の終了以降。
- 確定イベントは`EventPosition`の順にマージして、領域ごとの状態へ確定する。
- 影響: 被害者の結果が、終了の後、受付の封印を待つ分だけ遅れ得る。`host_clock`では、封印は世界時刻の進行に従う。

### 3.5 状態の持ち方

- 領域ごとに独立の状態とリビジョンを持つ。現行の「アクティブ1＋非アクティブ1」を、「同時に両方進む2領域」へ拡張する。
- 同時共有の使用中は、領域の切替（`isolated_assignment_duration_us`）は不要になる。

### 3.6 攻撃者から見えるもの

- 攻撃者が見られるのは、自分のジョブの状態・結果・宣言された時刻だけで、被害者の窓は見えない（tenant範囲の既存規則のまま）。双方向の漏れがあっても、被害者の活動記録そのものは公開されない。見えるのは、自分の量子ビットに入ったキックの結果だけ。
- したがって攻撃者が窓を重ねるには、被害者の実行の時機について、仮定として与えられた知識か、繰り返し実行による統計的な当たりが要る。被害者がいつ走るかの公開度は、課題プリセット側の仮定（難易度の軸の「情報公開」）とする。

## 4. 検査・不変条件

- `exclusive_fifo`では、既存のテストがすべてそのまま通る（回帰）。
- 同じ宣言入力なら、同じ重なり・同じ結果になる（決定性、ホスト遅延不変性）。
- 宣言された係数のない組み合わせには、効果が生じない。
- 重なりの有無は、隣り合うだけのジョブでは変わらない。
- 同じ領域に別tenantのジョブが重ならない。
- 1つの重なり群の中で、イベントの順序と確定位置が単調である。

## 5. 段階的な実装案

1. 型（`ExecutionWindow`・`DriveSchedule`）と、重なり判定・キック計算の純粋関数。
2. 単一ジョブの回路実行に、外部から与えたキックを時刻順に挟む機構と、手で与えたキックの試験。
3. キックとパルスレベルモデルの比較試験（向き・双方向の両方）。
4. 領域別FIFOと重なり群の計算・確定（実行器と状態の変更）。
5. 製品への接続（仮定の設定項目、根拠記録、公式ドキュメント）。
6. クロストークとGroverの課題プリセット・提出環境。

3以降は基盤の拡張で、お前と一緒に進める部分。

## 6. 未決定・リスク

- 計算を封印まで遅らせることの、`host_clock`での体験への影響（結果が遅れる時間）。現実のサービスもqueueと実行のあとに結果を公開するため、**許容する**（2026-10-17、D77）。遅れの大きさは実装時に測り、現実のqueue待ちとして不自然に長くないかを確かめる。
- 重なり群のジョブが途中で取り消されたときの扱い。双方向では、取り消しが相手の領域のキックも変えるため、群全体の再計算が要る。
- 関係の種類の登録と、manifestへの凍結の形（`relation_config`のどこに置くか）。
- 同じ領域内で別tenantが同時に走る共有は、この案の対象外とする。
- 事象の件数・命令作業量の上限（`max_events_per_job`、命令作業量上限）が、重なり群でどう効くか。
- キックの近似（時刻の粒度は命令の開始、回転は第1近似、多段の漏れなし）の精度は、3の比較試験で測る。

## 8. 遅延命令（実装済み、2026-10-17）

- 実サービスの対応物: Qiskitに`QuantumCircuit.delay`があり、OpenQASM 3にも`delay`がある。IBMのバックエンドは遅延の粒度などのタイミング制約を持ち、値は丸められる。[IBM AlignMeasures](https://docs.quantum.ibm.com/api/qiskit/0.44/qiskit.transpiler.passes.AlignMeasures)、[Qiskit Experiments BackendTiming](https://qiskit.org/ecosystem/experiments/stubs/qiskit_experiments.framework.BackendTiming.html)。AWS Braketではパルス記述の中で`delay`が使われている例を確認したが、ゲートレベルの回路で単独の`delay`が使えるかは確認できていない。[Braketの対応機能](https://docs.aws.amazon.com/braket/latest/developerguide/braket-openqasm-supported-features.html)。
- 本基盤の表現: 回路エディタの形式には元から恒等ゲート`I`があり、`params.duration_us`で継続時間を持てる。これを遅延として使う（新しい命令名は足さない）。`Circuit.delay(qubit, duration_us)`が書き出す。
- 物理: 指定した量子ビットだけが、その時間、待機モデルの緩和（T1・Tφ）を受ける。ほかの量子ビットには触れない。待機モデルが無い構成では拒否される。
- 時間の数え方: 同じ列のゲートは並列で、列の長さは最も長い継続時間。計画時間・実行器・実行の三か所で同じ式を使う。
- 上限: 1つの遅延は0〜10,000 µs。
- 現実との差: ゲートの間で空いている量子ビットが自動で待機として扱われるわけではない（実機ではそれも緩和する）。明示した遅延だけを待機として扱う。IBMの遅延の粒度による丸めは再現しない。

## 7. 現実のサービスとの関係

異なる利用者のジョブが同じQPUで同時に走ることは、IBMの公開資料では確認できない。クロストーク自体は研究で報告されているが、サービス方式は仮定である。仮定プリセットの根拠記録には「物理の裏付けはあるが、サービス方式は公開資料で確認できない」と書く（[比較 §5](service-time-and-workload-comparison.md#5-時間窓設計の追加確認2026-10-16)）。

## 9. 計算量の見積もり（2026-10-17、実測と訂正）

この開発機（12論理コア）で測った。**この機は時間帯により速度が3〜4倍変わる**（同じ測定が数倍遅くなる時期があった）ため、数値は幅で示す。最初に載せた「1命令・1shot約0.9 ms」は遅い時期の値で、速い時期の値は約0.2 msだった。相対的な大きさを見るためのもので、性能保証ではない。

プリミティブ（密度行列1つあたり、ミリ秒。速い時期〜遅い時期）:

| 量子ビット数 | 1量子ビットゲート | ゲート誤差（脱分極） | 全量子ビットの待機 | 1量子ビットだけの待機 |
|---|---|---|---|---|
| 4 | 0.02〜0.06 | 0.02〜0.07 | 0.08〜0.23 | 0.03〜0.09 |
| 6 | 0.03〜0.10 | 0.06〜0.20 | 0.20〜0.87 | 0.05〜0.20 |
| 8 | 1.6〜6.8 | 3.5〜11.7 | 3.9〜18 | 1.7〜5.2 |
| 10 | 21〜79 | 65〜232 | 156〜602 | 41〜124 |

ジョブ全体（製品経路、6 qubit、Grover回路）: 1命令・1shotあたり約0.2 ms（速い時期。遅い時期は0.7〜1 ms）。shot数と回路の長さに比例する。Grover2反復（約270命令）は60 shotで約3.5秒（遅い時期は約15秒）。

トレードオフの大きさ（速い時期の値。遅い時期は3〜4倍）:
- **命令作業量の上限**（現在32768、核の上限は65536）: 32768で1ジョブ最大約7秒。65536まで上げれば最大約14秒で、Groverは1ジョブ約120 shotまで届く。計算時間が主で、実サービスの性質ではない。
- **回路途中の待機ノイズ**（空いた量子ビットの緩和）: 層ごとに全量子ビットへ足すと、6 qubitで約0.2〜0.3 ms/層となり、1命令のコスト（約0.2 ms）の1倍強で、所要時間は約2倍。同じ結果を保ったまま、各量子ビットの待機を「次にその量子ビットを使うとき」にまとめて1回だけ適用すれば、1命令あたりの追加は1量子ビット分（約0.05〜0.08 ms）で、増加は約3割に収まる（精度の損失はない。待機は他の量子ビットへのゲートと可換だから）。現実性の上がり方は、回路が約17 µs、T1が数百µsなので数%。
- **領域の大きさ**: 6→8 qubitで、1命令あたり約17〜58倍。7は未測定。領域を広げる案は、計算量の面では割に合わない。
- **残留ZZの厳密計算**: 2領域の合計12 qubitの稠密行列。10 qubitの実測（ゲート21〜79 ms、脱分極65〜232 ms、待機156〜602 ms）から4^2倍で外挿すると、1命令あたり0.3〜10秒以上、行列1つ約268 MB。Grover1ジョブ（約16,000命令・shot）は数時間以上で、実用外。近似（条件付き位相回転の混合）は6 qubitの1ゲート相当で、コストは無視できる。
- **同時共有（2領域の独立計算＋キック）**: 領域ごとに独立に計算するので、計算量は領域数にほぼ比例（約2倍）。キックは1回あたり0.03〜0.4 msで、ジョブ全体では誤差の範囲。

### 近似・効率化の検討（試作の結果を含む）

- **同じ入口状態の再利用（試作して破棄）**: プログラムの測定前までは入口状態の決定的な関数なので、同じ入口状態で入るshotの計算を再利用する案を試作した。結果は同一に保てたが、効果はなかった。不完全なResetが前のshotの結果の記憶を残すため、入口状態がshotごとに異なり、再利用が起きない。この記憶はResetの漏洩という現象そのものなので、厳密な再利用では速くならない。
- **近似による再利用（候補、未実装）**: 前のshotの測定結果だけで入口状態を代表させ、それ以前の記憶（Reset成功確率pに対し(1-p)^2程度）を捨てれば、再利用が起きる。誤差を許容値で保証して（例えば入口状態の差のトレース距離が許容値以下のときだけ再利用する）、shotの統計ゆらぎ（1/√shot数）より十分小さくできる。ただしResetの長距離の記憶を近似で消すので、Reset課題の物理を変える。近似であり、トレードオフ（速度と、記憶の細部の損失）があるため、採否は判断が要る。
- **待機の遅延適用（厳密）**: 上記のとおり、精度の損失なしでコストを約1/3に抑えられる。回路途中の待機ノイズを入れるなら、この方法で入れる。
