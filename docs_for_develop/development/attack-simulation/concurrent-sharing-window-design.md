# 同時共有の時間窓の設計案

最終同期: 2026-10-17。**提案が中心で、未承認の部分が多い。** 実装・schemaの確定ではない。
合意済み: 漏れは最初から**双方向**を対象にし、拡張性を優先する（2026-10-17、[D76](decisions.md)）。それ以外の項目は未承認。
[仮定・過程変化・不変の基盤](assumption-process-model.md)（D74）が定める「基盤は一般機能として一度だけ拡張する」の、その拡張の中身を書く。
クロストーク専用機能にはせず、「複数のジョブの窓が時間的に重なる実行」を一般の方針として加える。

## 1. 現状（コードで確認した範囲）

- ジョブの窓は`JobExecutionWindow`（到着・開始・終了・公開）で、`DeclaredServiceTiming.plan_job_window`が1ジョブずつ計画する。開始は「到着＋処理遅延」と「直前のジョブの終了の直後」の遅いほうで、窓は構造的に重ならない。
- 実行器`DeclaredQpuExecutor`は進行中のジョブを1つしか持たず、開始時に`window.start < _physical_end`なら`single-region physical windows overlap`で拒否する。開始を確定した時点で、そのジョブの物理計算を一括で用意（prepare）する。
- 状態は`QpuStateStore`が正本で、1つの稠密行列（アクティブ領域）とリビジョン列を持つ。別領域（`tenant_dedicated_region`）は`InactiveRegionState`として保持するだけで、同時には進めない。
- 駆動の窓は`TimeWindow`（半開区間）と`ScheduledDriveInterval`で別に表され、`select_active_drive_transfers`が実装・試験済み。ただし、どこからも呼ばれていない。
- 確定イベント列は`EventPosition`（時刻・同時刻順）の単調列で、`seal_ingress`が「この位置までの受付は出そろった」という透かしを与える。

## 2. 提案の全体像

同時共有を、サービスのアーキテクチャ仮定の新しい値として足す。既定は現行と同じ。

| 項目 | 内容 |
| --- | --- |
| 仮定の名前 | `scheduling.concurrency_policy` |
| 値 | `exclusive_fifo`（既定・現行）／`overlap_disjoint_regions`（新） |
| 成立条件 | `placement_policy = tenant_dedicated_region`。領域は互いに素で、各領域は別の状態を持つ |
| 固定の時点 | 環境設定時。成立後は変えない（D74） |

`overlap_disjoint_regions`では、別tenantのジョブが互いに素な領域で、時間的に重なって走れる。同じ領域を共有するジョブは、従来どおり重ならない。

## 3. 設計の柱

### 3.1 窓の型を一本にする

`ExecutionWindow`（提案）= ジョブID・tenant・領域の物理量子ビット・`EventPosition`の開始と終了・`DriveSchedule`。

- `DriveSchedule`は、コンパイル済み回路から決まる「どの量子ビットを、窓の開始からの相対時刻で、どの回転角・位相で駆動するか」の列。shotの構造（命令時間、Reset、shot間待機）は決定的なので、窓の開始時刻が決まれば確定する。
- `TimeWindow`は`EventPosition`の時刻から作る読み取り用の見え方にして、別の正本にしない。
- ジョブの4点（到着・開始・終了・公開）は従来どおり持つ。

### 3.2 重なりの決め方

- 計画時に、宣言済みの所要時間だけから決める。ホスト時刻は使わない。
- `exclusive_fifo`: 従来どおり、開始は直前の終了の直後まで押し出される。
- `overlap_disjoint_regions`: 領域ごとのFIFOにして、他の領域のジョブの終了を待たない。開始は「到着＋処理遅延」と、**同じ領域**の直前の終了の直後のうち遅いほう。
- 重なりは、窓の半開区間[開始, 終了)の交差で定義する。隣り合うだけ（`[0,1)`と`[1,2)`）は重ならない。

### 3.3 効果のモデル（双方向・拡張可能）

窓の重なりが生む影響を、三つの部品に分ける。同時共有の基盤が知るのは部品の形だけで、クロストークという個別の事象は知らない。

1. **活動記録（`ActivityInterval`）**: コンパイル済み回路から、窓の開始からの相対時刻で、量子ビットごとの活動を取り出す。種類は`drive`（回転角・位相）・`measure`・`reset`・`idle`。`DriveSchedule`はこの列の別名にとどめ、駆動以外の活動も同じ型に載せる。
2. **関係（`CouplingRelation`）**: 環境作成者が宣言する、領域をまたぐ影響の規則。関係の種類の名前、向き（source→target）、係数を持つ。近似を伴う関係は、**近似モデルの選択**（`model`）も持つ。選択は環境設定時に決めてmanifestへ凍結し、成立後は変えない。厳密な計算が可能なものは`exact`を選べる。選んだモデルとその妥当な範囲、誤差の上限は、仮定の根拠記録と公式ドキュメントに載せる（D79）。種類ごとに、活動記録から`TimedEffect`の列を作る関数を登録する。今回実装するのは`drive_crosstalk`だけで、新しい種類を足すことが基盤の拡張になる。
3. **時刻付き効果（`TimedEffect`）**: 対象領域の状態へ、時刻順に適用する作用。種類は閉じた集合で、今回は`UnitaryKick`（回転）だけ。実装では、時間幅のある漏れ`DriveLeak`を、命令の間に置く回転`PlacedKick`にする（§10）。領域の実行器は、効果を時刻順に適用することしか知らない。

`drive_crosstalk`の具体:
- 環境作成者が`DriveCrosstalkTransfer`（複素係数）を向きつきで宣言する。**一方向でも双方向でも宣言できる**。双方向は、向きの違う2つの宣言で表す。攻撃者は選べない。
- source量子ビットの駆動が、相手の窓と重なる時間にあるとき、相手領域のtarget量子ビットへ「回転角＝|係数|×sourceの回転角、回転軸の位相＝係数の偏角＋sourceの位相」のキックを、その時刻に加える。`rz`は仮想で駆動なし。
- 双方向のとき、攻撃者の領域にも被害者の駆動のキックが入る。攻撃者の量子ビットが何もしない（`idle`）時間でも入るため、攻撃者は自分の量子ビットの変化から、被害者の駆動の存在や時機を読める。これが情報漏洩型の課題に使える経路になる。
- キックは「宣言された活動」だけから計算する。キックによって生じた活動が再び漏れる多段の経路は扱わない（第1近似）。
- 領域間は積状態のままにする。漏れは古典的な場による回転で、領域間のもつれは生じない。そのため2領域を同時に稠密に持つ必要がなく、各領域の状態は別々に進められる。
- 検証: 短い窓で、このキックが既存のパルスレベルの結合トランスモンのネットワークモデル（`core/pulse_transmon_network`）の結果と一致するかを比較試験にする。一致の許容は実測してから決める。

双方向でも循環依存は生じない。効果は、結果ではなく**活動記録**だけから計算される。サービスの回路は最後にまとめて測定する形だけを受け付け、測定結果に依存する条件分岐を持たないため、活動記録は測定結果に依存せず、窓の開始時刻が決まれば確定する。したがって、まず全ジョブの活動記録から全領域のキックを作り、次に各領域を独立に計算できる。**この性質は拡張時の不変条件**として扱う: 将来、途中測定や古典フィードバックを足すなら、活動記録が結果に依存するので、重なり群を時間刻みで同時に進める計算（共同シミュレーション）へ切り替える必要がある。

拡張の余地:
- `measure`・`reset`の活動を使う関係（読み出しの相関など）は、新しい関係の種類として足す（今回は実装しない）。
- **残留ZZ**は扱う（2026-10-17、[D77](decisions.md)）。ただし領域間にもつれを生み、積状態の仮定を破る。厳密な計算は2領域の合計12 qubitの稠密行列（4096×4096の複素数、約270 MB）となり、稠密計算の上限（8 qubit）を超えるため、計算量が爆発する。方針は段階とし、上の段階が計算量で成り立たなければ次へ進む: ①厳密に扱えるか（小さい構成で）を評価する → ②近似で扱う（**もつれの低ランク近似**を第一候補とする。2領域の結合状態を、領域Aの演算子と領域Bの演算子の積の和（演算子シュミット分解）で持ち、小さい項を切る。相手の占有確率を重みにした条件付き位相回転の混合は、相手がZ基底で静止している場合にだけ厳密で、エコーや重ね合わせの干渉があると外れるため、一般の近似には使わない。§11）。近似の誤差は、小さな構成での厳密計算との比較で測る → ③それでも不可なら扱わない（宣言された係数があっても効果を生じさせず、その旨を根拠記録に残す）。
- 攻撃者が「待つ」ための**遅延命令**は、サービスの命令として追加した（§8）。

### 3.4 計算と確定の順序

現行は、開始確定の時点でジョブの物理計算を一括で用意する。重なる相手が後から到着しうるため、同時共有ではこれを変える。

- ジョブの物理計算は、そのジョブと重なり得る受付がそろった後（`seal_ingress`がそのジョブの終了位置を越えた後）に行う。
- 重なるジョブ群を一つの「重なり群」として一緒に計算する。結果の公開は群の最後の終了以降。
- 確定イベントは`EventPosition`の順にマージして、領域ごとの状態へ確定する。
- 影響: 被害者の結果が、終了の後、受付の封印を待つ分だけ遅れ得る。`host_clock`では、封印は世界時刻の進行に従う。

### 3.5 状態の持ち方

- 領域ごとに独立の状態とリビジョンを持つ。現行の「アクティブ1＋非アクティブ1」を、「同時に両方進む2領域」へ拡張する。
- 同時共有の使用中は、領域の切替（`isolated_assignment_duration_us`）は不要になる。

### 3.6 攻撃者から見えるもの

- 攻撃者が見られるのは、自分のジョブの状態・結果・宣言された時刻だけで、被害者の窓は見えない（tenant範囲の既存規則のまま）。双方向の漏れがあっても、被害者の活動記録そのものは公開されない。見えるのは、自分の量子ビットに入ったキックの結果だけ。
- したがって攻撃者が窓を重ねるには、被害者の実行の時機について、仮定として与えられた知識か、繰り返し実行による統計的な当たりが要る。被害者がいつ走るかの公開度は、課題プリセット側の仮定（難易度の軸の「情報公開」）とする。

## 4. 検査・不変条件

- `exclusive_fifo`では、既存のテストがすべてそのまま通る（回帰）。
- 同じ宣言入力なら、同じ重なり・同じ結果になる（決定性、ホスト遅延不変性）。
- 宣言された係数のない組み合わせには、効果が生じない。
- 重なりの有無は、隣り合うだけのジョブでは変わらない。
- 同じ領域に別tenantのジョブが重ならない。
- 1つの重なり群の中で、イベントの順序と確定位置が単調である。

## 5. 段階的な実装案

1. 型（`ExecutionWindow`・`DriveSchedule`）と、重なり判定・キック計算の純粋関数。
2. 単一ジョブの回路実行に、外部から与えたキックを時刻順に挟む機構と、手で与えたキックの試験。
3. キックとパルスレベルモデルの比較試験（向き・双方向の両方）。
4. 領域別FIFOと重なり群の計算・確定（実行器と状態の変更）。
5. 製品への接続（仮定の設定項目、根拠記録、公式ドキュメント）。
6. クロストークとGroverの課題プリセット・提出環境。

3以降は基盤の拡張で、お前と一緒に進める部分。

## 6. 未決定・リスク

- 計算を封印まで遅らせることの、`host_clock`での体験への影響（結果が遅れる時間）。現実のサービスもqueueと実行のあとに結果を公開するため、**許容する**（2026-10-17、D77）。遅れの大きさは実装時に測り、現実のqueue待ちとして不自然に長くないかを確かめる。
- 重なり群のジョブが途中で取り消されたときの扱い。双方向では、取り消しが相手の領域のキックも変えるため、群全体の再計算が要る。
- 関係の種類の登録と、manifestへの凍結の形（`relation_config`のどこに置くか）。
- 同じ領域内で別tenantが同時に走る共有は、この案の対象外とする。
- 事象の件数・命令作業量の上限（`max_events_per_job`、命令作業量上限）が、重なり群でどう効くか。
- キックの近似（時刻の粒度は命令の開始、回転は第1近似、多段の漏れなし）の精度は、3の比較試験で測る。

## 8. 遅延命令（実装済み、2026-10-17）

- 実サービスの対応物: Qiskitに`QuantumCircuit.delay`があり、OpenQASM 3にも`delay`がある。IBMのバックエンドは遅延の粒度などのタイミング制約を持ち、値は丸められる。[IBM AlignMeasures](https://docs.quantum.ibm.com/api/qiskit/0.44/qiskit.transpiler.passes.AlignMeasures)、[Qiskit Experiments BackendTiming](https://qiskit.org/ecosystem/experiments/stubs/qiskit_experiments.framework.BackendTiming.html)。AWS Braketではパルス記述の中で`delay`が使われている例を確認したが、ゲートレベルの回路で単独の`delay`が使えるかは確認できていない。[Braketの対応機能](https://docs.aws.amazon.com/braket/latest/developerguide/braket-openqasm-supported-features.html)。
- 本基盤の表現: 回路エディタの形式には元から恒等ゲート`I`があり、`params.duration_us`で継続時間を持てる。これを遅延として使う（新しい命令名は足さない）。`Circuit.delay(qubit, duration_us)`が書き出す。
- 物理: 指定した量子ビットだけが、その時間、待機モデルの緩和（T1・Tφ）を受ける。ほかの量子ビットには触れない。待機モデルが無い構成では拒否される。
- 時間の数え方: 同じ列のゲートは並列で、列の長さは最も長い継続時間。計画時間・実行器・実行の三か所で同じ式を使う。
- 上限: 1つの遅延は0〜10,000 µs。
- 現実との差: ゲートの間で空いている量子ビットが自動で待機として扱われるわけではない（実機ではそれも緩和する）。明示した遅延だけを待機として扱う。IBMの遅延の粒度による丸めは再現しない。

## 7. 現実のサービスとの関係

異なる利用者のジョブが同じQPUで同時に走ることは、IBMの公開資料では確認できない。クロストーク自体は研究で報告されているが、サービス方式は仮定である。仮定プリセットの根拠記録には「物理の裏付けはあるが、サービス方式は公開資料で確認できない」と書く（[比較 §5](service-time-and-workload-comparison.md#5-時間窓設計の追加確認2026-10-16)）。

## 9. 計算量の見積もり（2026-10-17、実測と訂正）

この開発機（12論理コア）で測った。**この機は時間帯により速度が3〜4倍変わる**（同じ測定が数倍遅くなる時期があった）ため、数値は幅で示す。最初に載せた「1命令・1shot約0.9 ms」は遅い時期の値で、速い時期の値は約0.2 msだった。相対的な大きさを見るためのもので、性能保証ではない。

プリミティブ（密度行列1つあたり、ミリ秒。速い時期〜遅い時期）:

| 量子ビット数 | 1量子ビットゲート | ゲート誤差（脱分極） | 全量子ビットの待機 | 1量子ビットだけの待機 |
|---|---|---|---|---|
| 4 | 0.02〜0.06 | 0.02〜0.07 | 0.08〜0.23 | 0.03〜0.09 |
| 6 | 0.03〜0.10 | 0.06〜0.20 | 0.20〜0.87 | 0.05〜0.20 |
| 8 | 1.6〜6.8 | 3.5〜11.7 | 3.9〜18 | 1.7〜5.2 |
| 10 | 21〜79 | 65〜232 | 156〜602 | 41〜124 |

ジョブ全体（製品経路、6 qubit、Grover回路）: 1命令・1shotあたり約0.2 ms（速い時期。遅い時期は0.7〜1 ms）。shot数と回路の長さに比例する。Grover2反復（約270命令）は60 shotで約3.5秒（遅い時期は約15秒）。

トレードオフの大きさ（速い時期の値。遅い時期は3〜4倍）:
- **命令作業量の上限**（現在32768、核の上限は65536）: 32768で1ジョブ最大約7秒。65536まで上げれば最大約14秒で、Groverは1ジョブ約120 shotまで届く。計算時間が主で、実サービスの性質ではない。
- **回路途中の待機ノイズ**（空いた量子ビットの緩和）: 層ごとに全量子ビットへ足すと、6 qubitで約0.2〜0.3 ms/層となり、1命令のコスト（約0.2 ms）の1倍強で、所要時間は約2倍。同じ結果を保ったまま、各量子ビットの待機を「次にその量子ビットを使うとき」にまとめて1回だけ適用すれば、1命令あたりの追加は1量子ビット分（約0.05〜0.08 ms）で、増加は約3割に収まる（精度の損失はない。待機は他の量子ビットへのゲートと可換だから）。現実性の上がり方は、回路が約17 µs、T1が数百µsなので数%。
- **領域の大きさ**: 6→8 qubitで、1命令あたり約17〜58倍。7は未測定。領域を広げる案は、計算量の面では割に合わない。
- **残留ZZの厳密計算**: 2領域の合計12 qubitの稠密行列。10 qubitの実測（ゲート21〜79 ms、脱分極65〜232 ms、待機156〜602 ms）から4^2倍で外挿すると、1命令あたり0.3〜10秒以上、行列1つ約268 MB。Grover1ジョブ（約16,000命令・shot）は数時間以上で、実用外。近似（条件付き位相回転の混合）は6 qubitの1ゲート相当で、コストは無視できる。
- **同時共有（2領域の独立計算＋キック）**: 領域ごとに独立に計算するので、計算量は領域数にほぼ比例（約2倍）。キックは1回あたり0.03〜0.4 msで、ジョブ全体では誤差の範囲。

### 近似・効率化の検討（試作の結果を含む）

- **同じ入口状態の再利用（試作して破棄）**: プログラムの測定前までは入口状態の決定的な関数なので、同じ入口状態で入るshotの計算を再利用する案を試作した。結果は同一に保てたが、効果はなかった。不完全なResetが前のshotの結果の記憶を残すため、入口状態がshotごとに異なり、再利用が起きない。この記憶はResetの漏洩という現象そのものなので、厳密な再利用では速くならない。
- **近似による再利用（実装済み、2026-10-18、[D78](decisions.md)）**: 入口状態の差（トレース距離）が許容値以内の、同じジョブの先のshotの結果を再利用する。測定前までの過程はCPTP写像なので、トレース距離は増えず、1shotの誤差は許容値以内で、ジョブ全体の測定結果の分布の誤差は「shot数×許容値」以内に保証される（乱数は変えないので、差が出るのは乱数が摂動の幅に入ったときだけ）。距離の判定は、フロベニウスノルムの下限・上限で足りる場合は安価に、足りないときだけ固有値で厳密に行う。許容値は設定（`entry_reuse_tolerance`）で、0は厳密、製品の初期値は1e-5。Groverの120 shotの測定では、再利用の割合と所要時間は、許容値0で0%・13.1秒、1e-7で35%・9.5秒、1e-5で50%・6.8秒、1e-3で67%・4.8秒（約2〜2.7倍）。誤差の上限は、1e-5・1024 shotで1%。
- **待機の遅延適用（厳密）**: 上記のとおり、精度の損失なしでコストを約1/3に抑えられる。回路途中の待機ノイズを入れるなら、この方法で入れる。

## 10. 段階1の実装状況（2026-10-18）

段階1の「活動記録の取り出し」を実装した。選択関数（`active_drive_relations.py`）は元から実装済みだった。

- **パルス列の復元**（`native_pulses.py`）: コンパイルは、ゲートを`rz`・`sx`・`x`の列へ分解して時間と誤差を数えるだけで、パルスの中身（`rz`の角度）を捨てていた。ユニタリから`rz`の角度を求め、宣言されている分解（`rz`のみ、`x`、`x rz`、`rz sx rz`、`rz sx rz sx rz`）を解く。解けない並びは推測せず、そのゲートはパルス情報を持たない。`CircuitInstruction`に`natives`と、レイヤー規則に左右されないゲート自身の時間`intrinsic_us`を足した。
- **活動記録**（`shot_activity.py`）: コンパイル済みのProgramから、1shotの量子ビットごとの活動（`drive`・`frame`・`two_qubit`・`idle`・`reset`・`measure`）を、shotの開始からの相対時刻で取り出す。純粋な読み取りで、他のジョブも状態も見ない。shotの長さは計画時間の式と一致する。
- **位相の規約**: 仮想Z（`rz(a)`）は、その後のパルスの搬送波の位相を`-a`だけずらす。`drive`の`phase_rad`はこのハードウェア側の位相。各shotの先頭でフレームは0に戻る。ユニタリ（`rz`込み）から作った論理ゲートと、パルスを搬送波の位相で再構成したものが一致することを試験している。
- **キックの軸への変換（段階3で使う）**: 相手のハードウェア側の位相`alpha_hw = arg(係数) + phase_source`のキックは、相手の論理側（`rz`が実際の回転として入っているシミュレーション）では、その時刻の相手のフレーム`F_target(t)`を足して`alpha = alpha_hw + F_target(t)`の軸になる。`F_target(t)`は相手の活動記録の`frame`の累積から求まる。
- **窓・重なり・漏れ**（`concurrent_windows.py`、2026-10-18、2026-10-19に漏れを時間幅のある量へ変更）: `DriveSchedule`（1shotの活動記録をshot数・shot間待機・先頭のオフセットで繰り返す）、`ExecutionWindow`（ジョブ・tenant・物理量子ビット・開始と終了・スケジュール）、重なり判定（半開区間。接するだけは重ならない）、重なり群（連鎖でつながる窓の組）。漏れは`DriveLeak`: 相手の窓の内側にある、sourceの駆動の部分（時間区間、駆動全体の区間・角度・搬送波の位相・包絡線の形、係数、離調）を持ち、`rate(t) = 係数 × Ω(t) × exp(i(位相 + 離調×t))`が回転の速さ（絶対値、rad/µs）と軸の向き（偏角）を与える。`drive_crosstalk_leaks`（一方向。逆向きは窓を入れ替えて呼ぶ）、`leaks_into`（複数のsourceを時刻順に）、`gap_before`と`gap_leaks`（ジョブの間の隙間。起点は直前のジョブの終了、なければ時刻0。§12）。窓の端で切れた駆動は、窓の内側の部分だけが漏れる。領域を共有する窓の組は拒否する。
- **包絡線の形**（`pulse_shape.py`、2026-10-19）: `PulseShape`は面積1に正規化した[0,1]上の形で、`square`と、既存の`GaussianPulseEnvelope`と同じ切り詰めガウス（`truncation_sigma`）。活動記録の`drive`と`ShotActivity.pulse_shape`が持つ。形は較正データに無いので、宣言する仮定。サンプル値は`crosstalk_samples.py`（D80）。
- **離調**（`coherent_crosstalk.py`、2026-10-19）: `DriveCrosstalkTransfer.detuning_rad_per_us`。被害者の回転座標系で、漏れた場が`exp(i·離調·t)`で回る（駆動自身の離調と同じ符号の約定。tは評価時刻）。0は共鳴。
- **漏れの挟み込み（段階2、`kick_application.py`、2026-10-19）**: `place_kicks`が漏れを、shotと命令位置への回転`PlacedKick`（位置・物理量子ビット・回転ベクトル）にする。回転ベクトルは、シミュレーターの座標（仮想Zを状態の回転として入れる側）での、2次までのマグヌス展開 `r = ∫v dt + ½∬_{t1>t2} v(t1)×v(t2)`（`v(t)`は漏れの速さ×軸）で、`exp(−i r·σ/2)`が回転。2次の項は、軸が回る漏れ（離調がある駆動、回っている被害者から見た駆動）が正味の回転以外に生む分で、遠く離調した駆動ではそれが主な効果（AC Stark様の回転）。漏れを短いスライスに切って計算する。3次と、別々のsource間の交差項は無視する。軸には、置く時刻の相手のフレームF（`shot_activity.frame_before`。単独でも使える）を足す。被害者が自分のゲート（`rz`/`sx`/`x`）を実行している間の漏れは、そのゲートの相互作用表示（被害者の回転で戻した軸）で積分して、ゲートの直前に置く。それ以外の漏れ（待機、2量子ビットゲート、リセット、測定、プログラムのない量子ビット）は、漏れの開始より後に始まる最初の命令の直前に、その位置のフレームの軸で置く。窓の開始前（直前のジョブとの隙間、引き継ぎ）とshot間の待機の漏れは次のshotの先頭へ、最後のshotの終了後の漏れはそのshotが残す状態へ。実行器の`_execute_circuit(job, operation, kicks)`が置いた位置で回転を挟む。キックのあるshotは、入口状態の再利用（D78）の対象にも、再利用の元にもしない。プログラムの外の量子ビットはF=0。ネイティブ列を持たない1量子ビットゲートがあるとFは不明で、推測せず拒否する。リセットなしで状態を引き継ぐときのshotをまたぐFの扱いは未確認。
- **扱っていないもの**: 2量子ビットゲート（`CZ`）の磁束パルスの漏れ（`two_qubit`の区間は記録するが、効果のモデルはない）、測定パルスの漏れ。

## 11. 残留ZZの近似の検討（2026-10-18、実測）

Aを別のtenantの領域、Bを対象の領域として、`H = (ζ/4) Z_A Z_B` の結合のもとで、近似を厳密な2量子ビット計算と比べた。Bは|+⟩から始め、B側の ⟨X⟩⟨Y⟩ の最大差を見た（φ = ζ × 重なる時間）。

| ケース | φ=0.05 | φ=0.5 | φ=2.0 |
|---|---|---|---|
| Aが|+⟩のまま。静的な混合 | 0 | 0 | 0 |
| Aに途中でXパルス（エコー）。静的な混合 | 0.0003 | 0.031 | 0.46 |
| 同じ。区間ごとの混合 | 0.0002 | 0.016 | 0.23 |
| 同じ。古典的な経路を追う | 0 | 0 | 0 |
| AがH・待機・H・待機（Ramsey型）。古典的な経路を追う | 0.012 | 0.12 | 0.48 |
| 同じ。区間ごとの混合 | 0 | 0.001 | 0.059 |

- **静的な混合が厳密なのは、Aが計算基底で止まっている場合だけ**。Bの縮約状態は、Aの占有確率を重みにした混合に一致する。
- エコーでは、Aが反転しても|1⟩にいる時間は等しいという相関が要り、時間分解しない混合は外れる。
- 重ね合わせを通って再び干渉する場合は、経路どうしの干渉が効き、古典的な経路追跡も外れる。攻撃者の探り（Ramsey型）はこの形。
- どの単純な近似も全ケースでは合わないので、一般の近似としては採らない。

**もつれの低ランク近似**: 結合状態を、領域Aの演算子と領域Bの演算子の積の和として持つ。結合がなければランク1（積状態）で、結合のたびにランクが増える。ランクの上限を決めて小さい項を切る。3+3、4+4、5+5 qubitの領域で、1組が結合し、両領域がランダムな局所ゲートを6区間挟む構成を、厳密な全体の計算と比べた。

| 領域の大きさ | φ | 閾値1e-3でのランク | ランク16での誤差（トレース距離） | ランク32での誤差 |
|---|---|---|---|---|
| 3 | 0.1 | 7 | 2.7e-5 | 1.3e-6 |
| 3 | 2.0 | 21 | 4.8e-3 | 6.6e-4 |
| 4 | 0.5 | 10 | 4.8e-4 | 2.0e-5 |
| 5 | 0.1 | 7 | 2.0e-5 | 8.9e-7 |
| 5 | 0.5 | 10 | 3.9e-4 | 3.3e-5 |
| 5 | 2.0 | 28 | 1.4e-2 | 2.1e-3 |

- **必要なランクは領域の大きさにほぼよらず**、結合の強さ（φ）と結合する対の数で決まる。このため、領域を6 qubitにしても、同程度のランクで済む見込み（未確認。厳密な全体は12 qubitで計算できないため、直接は比べられない）。
- 結合が弱い（φ≲0.1）なら、ランク16で誤差は1e-4以下。結合が強い（φ≈2）でも、ランク32で約2e-3。
- 2対が結合すると、ランクは約1.5〜2倍に増える（3+3 qubitの測定）。

コスト: 1命令あたりの計算量は、ランクχ倍（その命令が作用する領域の側の全項に適用する）。χ=16で、独立計算の約16倍。ランクは閾値で適応的に決める（結合が弱ければ小さい）。誤差は、切り捨てた特異値から見積もる。

近似モデルは環境設定時に切り替えられる（D79）。`residual_zz`の`model`の候補は、`low_rank`（既定の候補。ランクの上限と閾値を設定に持つ）、`static_mixture`（相手がZ基底で静止する構成にだけ厳密。ほかでは外れることを根拠記録に明記し、選んだ場合は警告として残す）、`off`（効果を生じさせない）。`exact`は、領域の合計が稠密計算の上限以内の小さな構成にだけ選べる。

未決定: 領域間で結合する対の数と強さの宣言の形、ランクの上限と切り捨ての閾値の既定値、誤差の上限の示し方。

## 12. 漏れの再現とパルスレベルモデルの比較（段階3、2026-10-19）

`scripts/experiment_kick_vs_pulse_network.py`（試験は`tests/test_kick_vs_pulse_network.py`）。参照は、領域ごとに1つのトランスモン（結合なし、2準位）を既存の`ExtendedTransmonNetworkHamiltonian`で積分したもの（ハードウェアの見方。仮想Zは後続パルスの位相）。時間刻みを4倍細かくしても結果は1e-11以下しか変わらない。漏れの再現は、領域ごとに単独で、`leaks_into`と`gap_leaks`→`place_kicks`→実行器と同じ順の適用（シミュレーターの見方）で進め、最後にその領域の最終フレームで戻して比べる。領域間は積状態のままなので、各領域の純粋状態の忠実度で測る。パルスはsx/xの36 ns、角度は活動記録から。

**手順**: 最初の比較（点のキック）で見つかった不足を、ユーザーの判断（2026-10-19）で3つ足した。(1) 被害者が同時にパルスを打つときの相互作用表示、(2) 離調と包絡線の形、(3) ジョブの間の隙間の漏れ。足した後の結果を示す。続けて、サンプル値・隙間の起点・計算時間の優先を決めた（D80）。

**結果（1 − 忠実度。「漏れの大きさ」は、漏れを入れない場合の同じ量。定数は計算時間を優先した値）**

- 漏れがないとき、仮想Zを両側に入れても、2つの見方は1e-13で一致する（約束の確認）。
- **被害者が待機中・共鳴**: 全ての強さ（|c|=0.01〜0.3）・漏れの位相・形（正方形、ガウス）で1e-11以下。漏れの大きさは|c|=0.1で1.5e-2。
- **フレームと相互作用表示を抜くと**、被害者の`rz`の後では漏れの大きさと同じ誤差が出る（効果が丸ごと消える）。符号`+F`は解析（`Rz(φ)RxRz(−φ)`）と比較の両方で一致した。
- **離調あり（被害者は待機中）**: |c|=0.3で、30 rad/µsで2e-5、100で3e-5〜4e-5、300で5e-6〜7e-6（漏れの大きさは1.7e-1、5.6e-3〜6.3e-3、8e-4〜5e-3）。|c|=0.1ならさらに約10²分の1。2次のマグヌス項を入れる前は、100 rad/µsで漏れの大きさの80%（4.6e-3）が外れていた。遠く離調した駆動の効果は2次の項が主で、1次だけでは取れない。計算時間を優先した定数では、サンプルの離調（628 rad/µs）で、漏れの大きさの約1%が外れる（1.4e-6 対 1.6e-4）。
- **被害者が同時にパルスを打つ**: |c|=0.03で1e-10、0.1で2e-8、0.3で1e-6（漏れの大きさは2e-3、2.2e-2、1.9e-1）。相互作用表示を使わない点のキックは、|c|=0.1で1.9e-2で、漏れの効果がほぼ取れない。2つのパルスの開始がずれても1.4e-7以下。離調100 rad/µs・ガウスでも9e-9。
- **ジョブの間の隙間**: 被害者の2つのジョブの間に攻撃者の駆動が入る場合、隙間の漏れを入れれば1e-12で一致する。入れないと漏れの大きさ（|c|=0.3で2.1e-1）がそのまま外れる。
- **双方向**: 双方の窓が漏れを覆うとき、攻撃者側5e-8・被害者側3e-7（|c|=0.1）。

**前の記述の訂正**: 最初の比較では、双方向のとき攻撃者側の誤差が|c|=0.1で1.6e-2（漏れの大きさの40%）で、これを「被害者のπパルスの間に漏れの軸が回るのを、開始時の1回のキックで表せない限界」と書いた。**この原因の説明は誤り**だった。攻撃者の窓が始まる前（0〜0.05 µs）にも被害者の駆動は攻撃者の量子ビットに漏れていて、参照では作用するのに、再現はその前に直前のジョブがなく隙間の漏れを入れていなかった。隙間を時刻0から取ると9e-8になる。πパルスは限界ではなかった。

**隙間の起点**: 同じ領域の直前のジョブの終了から、そのジョブの開始まで。直前のジョブがなければ、世界時計の時刻0から（`gap_before`）。ジョブが始まるとリセットする量子ビットでは、隙間の漏れはそのリセットで消える（プログラムの外の量子ビットには残る）。領域の最後のジョブの後の漏れは、次のジョブの隙間として、そのジョブが決まったときに入る。

**残る限界**

- 2次までの近似。3次の誤差は漏れの角度の約6乗で、|c|·θ ≲ 0.5 rad（|c|=0.3まで）で上の値の範囲。別々のsource間の交差項は無視する。
- 2量子ビットゲート（CZ）の最中の漏れは、被害者の回転で戻さず、命令の間に置く（CZの磁束パルスと漏れの共存はモデルに無い）。測定パルスの漏れ・|2⟩への漏れ・DRAG成分・多段の漏れもモデルに無い。
- 比較の相手はこのプロジェクトの内部モデルで、実機との照合ではない。離調や包絡線の形は較正データに無く、サンプル値（`crosstalk_samples.py`: 離調は2π×100 MHz、包絡線はσ=継続時間の1/4で±2σに切ったガウス）を置く。サンプルであることは公式ドキュメントにだけ記載する。主張できるのは「宣言した仮定の下で、内部整合している」まで。仮想Zの位相は、パルスモデルの機能ではなく活動記録から組んだもので、Fの符号の確認はモデルと独立な証拠ではない。

**計算量**（この開発機、6 qubitのプログラム、8本の漏れの経路）: 計算時間を優先した定数（`SLICE_ANGLE_RAD`=0.8、`MAX_SLICES`=32、`SLICE_NODES`=4）で、漏れ1本あたり`place_kicks`は約0.1 ms。命令約190個・60 shotで約0.8〜1.0秒、命令約410個・60 shotで約1.7〜2.3秒（離調0〜1900 rad/µs）。同規模のジョブの物理計算（Groverで約3.5秒）の1/4〜1/2。**時間は定数にほとんど依らず**（スライスを5分の1にしても10%しか変わらない）、漏れ1本あたりの呼び出しの固定費が支配する。効いた削減は、共鳴の漏れで軸が変わらない部分を閉じた式（`DriveLeak.net_rotation`）にしたことと、numpyの小さな呼び出しの整理で、最初の約3〜4倍速い。さらに削る道（未実装）: 同じ幾何の漏れをまとめて配列で計算する。離調0で被害者と攻撃者のshotの周期が同じなら、shotごとの結果を再利用する。

**決定（D80）**: 離調と包絡線はサンプル値を置き、サンプルであることを公式ドキュメントにだけ記載する。隙間の起点は時刻0。計算の定数は計算時間を優先する。
