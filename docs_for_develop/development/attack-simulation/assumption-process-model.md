# 仮定・過程変化・不変の基盤

最終同期: 2026-10-16。設計思想の記録で、schema・実装の確定ではない。
「合意」はユーザーが明示または承認した内容、「提案」はAIの案で未承認。2026-10-16に§3〜§5の提案はユーザーが承認した（§5のGrover規模は4量子ビットへ変更、妨害判定のゆらぎ基準は実装中の実験で定める）。

## 1. 「攻撃」の定義（合意）

本書でいう攻撃は、量子サービス上で攻撃者・被害者・サービスの間に起きる、サービス上の操作によって引き起こされるものを指す。
過程で攻撃者の操作可能な範囲が広がったり縮んだりすることはあるが、それはサービス側の状態変化の結果であって、
攻撃者へ権限が突然与えられることではない。

## 2. 三層の分離（合意）

| 層 | 内容 | 変わる時点 |
| --- | --- | --- |
| 仮定 | 攻撃者の権限、サービスが提供する機能、アーキテクチャの詳細、被害者の条件 | 環境設定時に固定。成立後は変えない |
| 過程変化 | 仮定が定めたサービス環境の上での自由度の変化 | 過程中。サービス状態の変化として生じる |
| 基盤 | シミュレーター内のサービス、API、機能の境界 | 仮定に依存せず、原則変化させない |

- 仮定は、基盤の既存機能を「選ぶ・設定する」だけで、基盤にない機能やエンドポイントを増やさない。
- 過程変化は仮定の外へ出ない。仮定が上限であり、別の上限概念は置かない。
- 基盤を変えるのは、新しい物理や操作が必要なときだけで、課題の追加では触らない。変える場合は一般機能として一度だけ作る。

## 3. 過程変化の扱い

- 攻撃者へ権限を与えるイベントは存在しない。攻撃者の操作可能範囲は、サービス状態・役割・仮定から導かれる射影として扱う（合意）。
- 持つ状態は物理状態、サービス状態（割当・キュー・実行窓・クォータ・Reset方針の適用状況）、観測状態の三つ（合意）。
- 状態を変えるのは、攻撃者の操作、被害者の操作、サービス方針による処理の三つで、いずれも既存と同じ確定イベント列を通す（合意）。

## 4. 自由モードと課題モード（合意）

- 自由モードと課題モードは区別する。
- 課題モードは、一つの自由モード上でも再現できる状態のプリセットを持つ。特定の課題に依存してはならない。
- 課題モードは、必要に応じて提出環境を提供する。
- 妥当な仮定プリセットと難易度を課題モードに適用する。
- 仮定の根拠や難易度の軸の説明は、操作画面に出さず公式ドキュメントへ記載する。

合意: 課題固有のコードをruntimeへ入れず、課題の受け入れ条件に「プリセットを自由モードへ読み込むと、課題用コードなしで同じ事象が再現する」を置く。
採点器・隠しケース・flag発行は提出環境側に置き、基盤は採点を知らない。
難易度は別の機構にせず、プリセット内の仮定の値で表す。軸は共通の少数（観測量・ノイズ・情報公開）に固定する（合意）。

## 5. 適用例: クロストークとGroverの妨害（合意）

- 基盤の拡張として必要なのは、サービスのアーキテクチャ仮定にもともとある「同時共有」の実装のみ。クロストーク専用機能にはしない。
- 同時共有のスケジューラは、ジョブを「tenant、量子ビット集合、開始・終了の装置時刻、駆動内容」を持つ窓にする。FIFOは窓を重ねない方針、同時共有は「サービス仮定が許し、かつ領域が隣接している場合だけ重なりを許す」方針とする。重なりは受付時に宣言済みの所要時間から決め、窓の開始・終了を既存の確定イベント列へ載せる。
- 課題側は、同時共有を選んだ仮定プリセット、被害者のGrover workload、提出環境の採点で構成する。
- 攻撃者が持つのは自分のジョブ送信権だけで、被害者ジョブとの時間窓の重なりは、スケジューラ状態から結果として生じる。
- 被害者のGroverは4量子ビット（16候補）とする。
- 妨害の判定は、同じプリセット・同じseedで攻撃者が何もしない場合の成功確率を基準とし、そこからの低下量で行う。攻撃者の駆動予算（総振幅と総時間）はプリセットの難易度の値とする。低下量が統計ゆらぎを超えたかの判定基準は、実装中の実験で定める。

## 6. 未決定

- Groverの反復数とoracleの置き方。4量子ビットの多重制御Zは、ネイティブのCZだけでは補助量子ビットか深い回路が要る。回路が長いほどノイズ下の基準成功確率が下がるため、領域（6 qubit上限）と回路長で成立するかは未検証で、実測してから決める。
- 妨害判定のゆらぎ基準と、駆動予算の具体値。
- 同時共有でのクロストーク係数の与え方（環境作成者のパラメータとして、攻撃者が選べるジョブ設定と区別する）。
- 既存の`reset_leakage_*`のうち、課題固有のものと共通にできるものの仕分け。

## 7. 既存コード・文書との照合（2026-10-16）

整合していた点:
- `SharedQpuRuntime`は「モード非依存」で、課題の判定・難易度・課題名を知らない。課題プリセットは`api/attack_challenge.py`が設定値だけで組み、採点は同ファイルの評価器（提出環境側）にある。
- 権限は`attacker.operation_grants`・`victim.operation_grants`・`qpu_service.supported_operations`・`ScenarioPolicy.allowed_operations`としてmanifestに凍結される。過程で権限を与える経路はコードにも文書にも無い。
- `ScenarioMode.CHALLENGE`で分岐するのは、採点可能な課題の許可項目がロックされているかの検査（`job_authorization.py`・`scenario_compiler.py`）だけで、物理や操作の挙動は変えない。

修正した点:
- 共通の`attack_path.py`にあったReset課題の値（`RESET_LEAKAGE_MECHANISM`、`reset_leakage_attack_path_config`）を`reset_leakage_path.py`へ移した。共通側は経路の宣言形式だけを持つ。

修正した点（続き）:
- Reset課題の旧単独経路（`reset_leakage_scenario`・`preflight`・`acceptance`と、それを使う試験・検証スクリプト）を削除した。製品経路は採点器・設定値・分析補助だけを使い、`SharedQpuRuntime`を通る。これに伴い、`ResetLeakageHiddenGrader`、設定値のうち受入判定専用のもの、`ResetLeakageRuntimePlan`に依存していた旧検証を外した。攻撃経路宣言の検査は`AttackPathDeclaration`で試験を残した。
- 設定画面の「根拠」表示を削除し、各設定項目の根拠を公式ドキュメント（`formalweb/website/docs/limitations/attack-simulator.md`の「設定項目の根拠」）へ移した。サーバーの設定目録は`basis`を引き続き保持し、manifestへ凍結する。D73が定めた「較正値の根拠を近くに表示」はこの合意で置き換える。

残る注意:
- 削除した旧検証のうち、FTQC方式の拒否は`circuit_program.py`が製品経路で行っているが、専用の試験は残していない。
