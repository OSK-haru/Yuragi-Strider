# 資格情報の受渡方式と環境成立境界

- 課題モードの攻撃者は、プリセットが指定した仮想接続プロファイルを使う。被害者runnerの認証主体・資格情報は別管理とし、攻撃者へ渡さない。
- 自由モードでは環境成立前に `attacker.credential_delivery` を変更できる。現時点の選択肢は `preconfigured_profile`（接続済みプロファイル）と `manual_simulated_credential`（シミュレーターが発行した仮想資格情報を利用者が手動設定する想定）。両者の発行元は `attacker.credential_origin=simulator_issued` というシナリオ仮定に記録する。利用者が任意文字列を作って資格情報にする方式は採用せず、未対応の値を拒否する。`qpu_service.supported_credential_deliveries` にない方式も採用できない。
- これらは実在のAPIキーではなく、シナリオの接続・認証仮定である。実資格情報を設定ファイル、manifest、ログに保存しない。内部runtimeでは環境ごとに高エントロピーの仮想資格情報を発行し、認証前にはジョブを受け付けない。課題プリセットの `preconfigured_profile` は攻撃者接続へ自動設定する。`manual_simulated_credential` は攻撃者用の値を一度だけ取得し、接続へ設定するまで操作できない。被害者runnerの値は別発行・非公開で、環境終了時には双方を失効させる。資格情報はmanifestやジョブ応答には載せない。
- 認証した主体は既存のジョブサービスへ渡し、サービス・役割・シナリオ・tenantの認可を引き続き適用する。これは信頼されたプロセス内の境界であり、任意Pythonコードを実行できる攻撃者から内部オブジェクトを守るサンドボックスではない。疑似ターミナル、HTTP認証adapter候補、UI部品は実装済みだが、HTTPは未mount・UIは未接続。永続化・復旧時の資格情報の扱いは未実装。
- `ScenarioEnvironment.set_assumption` は自由モードの準備中だけ許す。`establish` で検証済みmanifestを確定し、その後は全シナリオ仮定の変更を拒否する。再設定する場合は環境を破棄して新しい環境を作る。表示・操作性のみの設定は別系統とする。既存のcompilerを直接呼ぶコードはこのライフサイクルを経由していないため、今後の画面/API接続では必ずこの境界を通す。
- 実サービスとの対応: IBM Quantumは保存済みアカウントまたは明示的なAPIキー、Amazon BraketはAWSのプロファイル/IAM権限を用いる。ここで再現するのはその接続方式・権限境界であって、実サービスの鍵や完全な認証プロトコルではない。サービスごとの適用可否はシナリオで明示する。

## 環境管理者とサービス発行の境界（2026-10-04合意）

メタ層の環境管理者は環境構成・成立・棄却と復旧管理を担当し、模擬QPUサービスの通常tenantとは別の主体とする。攻撃者のサービス資格情報でメタ管理操作を認可しない。

参加者の仮想資格情報の発行・検証・失効は下位のQPUサービス側の責務とする。メタ層は確定したservice profileを構成し、発行処理を適切な境界へ委譲する。既存の`simulator_issued`は本製品内で発行する仮想資格情報という出自であり、メタ管理者が模擬サービス外から無制限に権限を与える意味ではない。発行をサービスへ置くことも、通常tenantの無認可発行APIを追加する意味ではない。

環境管理者の設定は自由／課題の両modeで開始前（環境成立前）だけ変更可能とする。課題では開始前でもpresetの固定・秘匿規則を維持する。成立後と復旧再開中は管理者権限・主体の対応・サービス発行方針を変更しない。既定の管理権限による棄却・復旧操作と、管理者設定の編集は区別する。表示・操作性だけの設定は別系統のままとする。

責務配置と設定凍結に加え、D57で実公開Webの登録不要ブラウザ所有sessionとserver正本を採用した。これは実サイトの所有者認証であり、模擬サービスの仮想参加者資格情報とは別。具体的なHTTP/UI認証形式・bootstrap・発行API・復旧時の再接続／再発行手順は未確定・未実装。現在の`VirtualCredentialAuthority`は内部実装、`AttackSession.close()`は失効・実行終了待ち・binding解放であり、復旧再開ではない。[v1のWeb／復旧契約](common-foundation-v1-contract-proposal.md)と[復旧境界](runtime-boundaries-and-resolutions.md#42-フォールバックとしての再開2026-10-04合意)を参照。
