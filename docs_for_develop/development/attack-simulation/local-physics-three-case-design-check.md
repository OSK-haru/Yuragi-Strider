# 局所物理共通設計の三事例点検

状態: **設計上の試行・未検証**。以下の量子ビット番号、event列、配置は矛盾を探すための例であり、課題プリセットや実サービスの保証ではない。2026-10-01。

対象は[局所物理近似の共通契約案](local-physics-approximation-contract-proposal.md)の「有効関係と持越し相関から計算領域を選ぶ」「必要相関を保てない構成は物理実行前に拒否する」という二原則である。各例で、受付可能なジョブ、物理event、必要状態、観測を同じ順に追う。

## 1. 順次再利用と不完全Reset

例: 被害者が物理量子ビット`q7`に秘密bitを符号化するジョブを実行する。QPU serviceがtenant交代時にReset eventを入れ、その後、攻撃者が`q7`を測定するジョブを実行する。両ジョブは別の`ServiceJob`で、Resetはservice-owned eventである。攻撃者が受け取るのは自分の測定結果だけとする。

- 領域選択: 二つのジョブが同時でなくても、`q7`の持越し状態とReset channelをつなぐ。単一量子ビットの例では`q7`の局所状態で足りる。
- 捨てられない情報: 被害者の入力に依存するReset前の状態、Reset後の残留、装置時刻とevent順序。`P(attacker=1 | victim bit)`の差と、完全Reset時にその差が消えることを調べる。
- 境界例: 被害者が直前に`q7`と`q8`をもつれさせ、後続ジョブが`q8`にもアクセスする場合、`q7`だけの状態では後続の共同観測を保証できない。Reset失敗枝が相関を持ち越すなら、相関を保つ状態表現か検証済み縮約が必要になる。

この例の成立には、同一量子ビットへの順次割当と攻撃者による自己測定が必要であり、queueでの隣接だけを物理的隣接と混同しない。

## 2. 同時実行と駆動クロストーク

例: 攻撃者の`q10`への駆動と、被害者の`q11`上の回路を同一物理windowに配置する。設定には`q10`の制御源から`q11`への非零の伝達係数を置く。攻撃者は自分のジョブ、被害者は自分のジョブを送る。被害者側出力の変化が目的なら、その出力を攻撃者が知る経路は別途設定する。

- 領域選択: 二つの駆動時刻が重なり、伝達辺が有効なwindowを含める。`q11`の有効駆動は両ジョブの波形を時刻整列して計算する。単にqueueで前後しただけなら、この瞬時伝達モデルによる干渉は起きない。
- 状態表現: 制御源の波形が既知の古典信号で、`q10`と`q11`間に量子結合や先行相関がなければ、共通の時刻表を使った局所状態の別計算も候補になる。制御伝達辺でつながることだけを、結合密度行列が必須という根拠にはしない。
- 結合条件: 有効な残留ZZ・交換結合や先行相関があれば共同状態を保持する。window終了後に結合を止めても、残る相関を自動で破棄しない。
- 観測: 被害者の出力変化と攻撃者が実際に取得できる証拠は分ける。被害者結果を公開しない設定で攻撃者の成功を「結果を見た」こととして判定しない。

現行FIFO runtimeは同時windowを構成せず、単一量子ビットしか受け付けない。この例には、複数ジョブを一つのwindowへ束ねるscheduler policy、割当の整合、単一writerによる一回の物理更新が要る。

## 3. 相関Readoutと結果投影

例: 被害者の`q20`と攻撃者の`q21`を同じ読出しwindowに入れ、二量子ビットの共同混同行列を適用する。真のbit列から共同の報告bit列を生成し、各主体へ自分に許された結果だけを返す。

- 領域選択: 読出し共有グループと同時測定時刻をたどる。量子状態が独立でも、報告値の共同分布には読出しグループ全体を含める必要がある。共同量子状態が必要かどうかは先行結合と持越し相関で別に判定する。
- 漏洩成立条件: 攻撃者へ返す周辺分布が被害者の真のbitに依存する混同行列なら、攻撃者自身の結果から推定が可能になり得る。単に二つの報告bitが相関するだけでは、秘密の推定可能性は結論できない。
- 境界例: 読出しが別時刻なら、現行の静的な共同混同行列だけではジョブ間漏洩を作れない。時間をまたぐ読出し系の記憶を主張するなら、寿命と更新規則を持つ別のslow stateが必要になる。
- 観測: 真の共同bit列、共同誤分類、相手の報告bitは内部証跡とし、通常は攻撃者へ渡さない。攻撃者へ渡すのは自分の結果の投影だけである。

現在の`CorrelatedReadoutChannel`は、同時に与えた共同確率へ静的channelを作用させるprimitiveである。共有windowの生成、物理状態の測定後更新、主体別の結果投影は、このprimitive単体では行わない。

## 4. 三例を通した判定

同じ選択原則で三例を記述できる。ただし、関係辺が結ぶ対象は同じではない。Resetは**時刻をまたぐ量子状態**、駆動伝達は**同時の制御信号**、Readoutは**同時の報告値**を結ぶ。計算領域を一つの連結成分や一枚の密度行列と同一視すると、不要な結合計算を増やすか、必要な相関を落とす。

設計上の共通手順は、(1) jobとservice eventから物理windowを確定、(2) windowで有効な関係と正本に残る相関を集める、(3) 量子状態・制御波形・読出し確率の各計算対象を決める、(4) 必要な操作と出力を保つ表現・資源見積りを検査、(5) eventを単一の状態権限で確定、(6) 結果を主体別に投影、となる。これは設計候補であり、schemaや実装の確定ではない。

## 5. 見つかった欠落と次の設計判断

1. **preflightの時点。** 課題プリセットで既知のevent列はscenario開始前に検査できる。自由モードで未来のジョブ列は確定しないため、現在状態・既存予約・新規jobを合わせた物理windowを、受付／割当前に再検査する必要がある。将来の未知ジョブまで開始時に保証したことにはできない。実行中に新たな重なりが生じる場合も、物理eventより前に計画の整合を確認する。
2. **状態の分割と結合。** 現行の`QpuStateSnapshot`は固定された一領域の密度行列を保持し、量子ビット集合の増減や複数領域の相関追跡はしない。将来の正本には、領域のmerge/split、相関の来歴、既存revisionと原子的に整合する更新規則が必要。相関が消えたと証明できない限りsplitしない。
3. **schedulerと割当。** クロストークと共同Readoutは、別tenantの同時windowをサービス設定が許すときだけ成立する。排他対象は物理量子ビットの重複と、共有制御／読出し資源の衝突条件から決める必要がある。FIFOが唯一の方式なら、この二例は実行できない。
4. **読出しの状態更新。** 報告bitの混同行列だけでは、測定後にどの量子状態が残るか決まらない。後続ジョブを評価するには量子測定のinstrumentまたは同等の状態更新契約を先に定める。
5. **複合機構の検査。** 駆動伝達とZZ、Resetと先行もつれ、共同Readoutと先行結合が重なると、各機構単独で使えた縮約の前提が崩れ得る。小規模の結合参照計算と後続jobの観測で、許可済み近似の適用範囲を検証する。

次は三例に共通する`window / relation / carried-state / observable / result-projection`の最小入力と、受付時・開始時・実行直前の検査責務を定義する。そのうえで小規模の具体的event列と負の対照をテストへ落とす。今回行ったのは文書と実装境界の照合であり、数値実験やruntime検証ではない。
