# 一般サービスモデルと特殊化可能性

2026-10-04。状態: **特殊化可能な共通構造を要求する方針は合意（D55）。以下の定義・対応案・確認手順はその具体化であり、形式的証明や個別サービス実装の完了ではない。**

## 1. 要件との対応と範囲

目的は量子固有のインシデントを、共通の操作・物理基盤上で体験できること（D13/D14/D40/D41）。課題／自由は同じ基盤（D07）で、成立条件は宣言された共有資源・経路（D48）。サービス差は権限・配置・時間・観測として表す（D20/D23/D37/D50）。特殊化可能性は、この要件をReset専用の例外なしに満たすための設計条件である。

一般モデルを一つのFIFOサービスと同一視しない。現FIFOは共通構造の一つの実装profile（D25）であり、全サービスの普遍規則ではない。サービスごとの完全なSDK、クラウド基盤、課金、運用、内部物理過程を先行実装する要求でもない。

対象サービス、時点、機能、比較する観測・時間精度を限定して対応を示す。未公開の内部仕様や未測定の物理間隔を推測して、全サービスに特殊化可能と宣言しない。

## 2. 共通構造と選択する方針

共通構造は、主体・資源・要求・job・予約等の状態と、その状態を変えるevent、物理エンジンへの作用、主体別の観測投影を持つ。部品を増やすこと自体を目的にせず、既存manifest、認可、状態所有、Program境界、時計／event境界へ責務を対応させる。

profileで意味を定める箇所:

- 受付・認可: 入力形式、operation能力、主体／tenant scope、受領／受理／拒否。
- queue・専有: 実行対象を選ぶ規則、優先度、順序保証、予約対象・期間・開始／失効条件。
- 割当・物理作用: resource binding、再割当、Reset、宣言待機、対応する物理model。
- job lifecycle: 実行段階、取消・失敗・再送・結果確定の意味。模擬故障とhost例外を分ける。
- 観測: 主体に返せる状態・結果・queue情報・時刻、公開可能時点、粒度。

単なるboolean追加ではなく、版付きの方針・制約・単位付きparameterで表す。どの組合せも自由に成立するわけではない。変更は環境成立前のみ、課題はpresetで固定、実行値は既存resolved manifestを正本とする。

**形式に設定を保存できること、意味を定義できること、runtimeが実行できることは別。** 未実装の方針を指定した場合、runtimeは開始前に拒否し、FIFO等へ黙って置き換えない。将来新しい一般機構が必要になれば共通構造の拡張はあり得る。「個別サービス実装を今しない」は「任意の未知機構も設定だけで表現できる」という意味ではない。

## 3. 特殊化の定義と確認義務

`G(P)`を共通構造へprofile Pを適用したモデルとする。対象サービスS、比較範囲Bについて次を残す。

1. **範囲B**: 対象サービス／時点／機能、入力集合、観測項目、時間精度、確率的比較の許容誤差、対象外。
2. **対応写像**: Sの入力・主体・状態・event・観測を、共通モデルへ対応付ける。サービス予約sessionと本製品の環境sessionを同一視しない。
3. **profileの構成例**: 方針と制約を具体的に選んだPを示す。方針名だけでなく、実行可能条件と状態遷移の意味を定義する。
4. **対応の確認**: Bで要求した許可／拒否、進行、実行順序、状態保持、観測が対応することを示す。情報の追加公開、禁じた割込み、暗黙Reset、host遅れの物理化を認めない。
5. **不足**: 不明、追加模擬仮定、構造では表せない条件、runtime未対応を個別に記す。

目標の表記は `抽象化_B(S) ≈ 観測_B(G(P))`。≈の条件はBで定義し、内部eventの隠蔽やtime粒度の丸めを含めても、比較対象の因果関係を消さない。物理的な待機を表示の都合で圧縮しない。

一方向の「模擬traceが禁止仕様へ違反しない」だけでは、全要求を拒否する空の実装も合格してしまう。範囲Bで宣言した操作と進行を実現できることも確認する。逆に、資料が公開していない全trace／確率分布との同値性は証明できない。公開資料だけの確認は**仕様片への制約対応**と記し、完全同値の証明とは呼ばない。

順序非保証は許される複数順序として表せるが、その確率が不明なら一様乱数等を実サービスの事実として採用しない。観測されない秘密状態を落とす抽象化も、必要な物理作用・将来の漏洩を消すなら不適合。

## 4. サービス仕様片への対応例

以下は公開一次資料で確認した条件を共通方針へ対応させた**設計上の構成例**。各サービス全体の特殊化可能性を証明したものではない。既存manifestの正式field名へ追加した値でもない。

### IBM active sessionの専有

[IBM実行mode](https://quantum.cloud.ibm.com/docs/en/guides/execution-modes)は、activeなsessionの専有、他利用者／校正jobを入れないこと、最初のjobの通常queue待ちを説明する。

対応案: 予約方針がresource・workload scope・開始／失効条件を保持し、実行候補の条件へ`active予約の対象workloadに属する`を追加する。予約開始前は通常の選択規則へ渡す。反例は「予約active中に無関係tenant jobが実行される」で、禁止する。予約の全TTL／取消仕様、instance権限、API schema等はこの例の確認範囲外。現runtimeはこの予約方針を実行していない。

### IBM batchの投入順非保証

[同資料](https://quantum.cloud.ibm.com/docs/en/guides/execution-modes)はbatchの投入順を保証せず、専有でもないと説明する。

対応案: batch内の実行候補集合に、投入順を唯一の許容順とする制約を付けない。前処理・依存・資源制約を満たす順序を許す。反例は「共通構造が常にFIFO順以外を表せない」で、一般モデルの欠落と判定する。具体的な選択確率や他利用者との物理同時駆動は、この記述から推測しない。現runtimeはFIFO以外を実行できない。

### AWS Braketの優先queueとqueue観測

[Braket queue仕様](https://docs.aws.amazon.com/braket/latest/developerguide/braket-task-when.html)は通常taskとHybrid Jobs由来taskの優先差、queue depth、自分のqueue positionを説明する。

対応案: 出自／権限を検査したpriority classを受付で確定し、実行候補を優先規則で選ぶ。攻撃者が任意ヘッダーだけで上位優先へ昇格できるようにしない。queue投影は公開深さ／自分の位置だけを返し、他者回路・識別子・精密時刻を追加しない。同着細則、全公平性条件、latency分布、物理割当は未確認として残す。現runtimeはこの優先方針を実行していない。

## 5. 現時点の到達点

既存実装にはmanifest凍結、capabilityとgrantの合成、主体別投影、単一QPU/FIFO、queued取消、revision付き状態所有、明示時刻metadata、明示待機の内部kernelがある。`SharedQpuRuntimeConfig`は非FIFO／非queued-only取消を拒否する。一般JSON fieldへ任意情報を保存できても、予約・priority・batch選択が動く証拠ではない。

この文書は共通構造へ必要な意味と三つの仕様片の対応案を示した段階。特殊化schema、方針の状態遷移の完全定義、状態対応による形式的証明、実行checkerは未完成。個別provider実装を開始する承認ではない。

## 6. 初回完成までの区切りと再検討条件（作業案）

最初の区切りは、現FIFO profileと専有／順序変更／優先・観測の仕様片を使い、共通境界に意味の矛盾がないかを確認すること。形式的な特殊化の確認は対象を限定して続けるが、全サービスの対応完了を初回体験の着手条件へ拡大しない。詳細な証明手順・schemaは提案段階として扱う。

追加レビューは、権限・経路・順序・状態寿命・観測・資源上限のいずれかで、具体的な反例や新しい要件が生じた場合に絞る。既存合意を根拠のない懸念だけで毎回白紙へ戻さない。名前やAPI表記の差だけならadapterの対応として扱い、共通構造を増やさない。

初回に不要なprovider別SDK、全料金plan、全運用故障、万能なpolicy言語、証明専用の追加依存は先行実装しない。次の成果物は限定範囲のprofile意味論と反例検査で、実サービス全体の再現保証ではない。[進捗](progress.md)、[サービス時間比較](service-time-and-workload-comparison.md)、[仮定管理](assumption-handling-contract.md)を参照。
