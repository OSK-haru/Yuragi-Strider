# 実行表現の選択

## 方針

回路意味論は `CircuitConfig` に統一し、計算表現だけを実行開始時に選択する。

| 条件 | 表現 | 計算量の目安 |
| --- | --- | --- |
| 1〜8量子ビット、ノイズあり | Density Matrix | $O(4^n)$ メモリ |
| 6〜18量子ビット、理想・測定なし | Statevector | $O(2^n)$ メモリ |
| 将来の大規模ノイズ | Trajectory（予約） | 軌跡数 × $O(2^n)$ |

自動切り替えのしきい値は 5 量子ビットで、これは密度行列経路の上限ではなく
「理想条件でより安い表現へ移る点」である。6〜8量子ビットでもノイズがあれば
密度行列経路で実行される。9量子ビット以上でノイズを含む要求は拒否される。
なお明示的CPTPは $4^n\times4^n$ の Liouvillian を構成するため、
ノイズありでは5量子ビットまでに制限され、6〜8量子ビットはRK4のみとなる。

現在のStatevector経路は、理想・測定なし回路で有効化される。中間測定を含む回路は、
測定スナップショットと混合状態の意味論を壊さないため、現段階では既存の分岐密度行列
経路を使用する。

Circuit Studio の新規実行設定は `rust_dense_preview` を選ぶ。対応する理想回路では
ゲート列と読み出し割当を一度の PyO3 呼び出しでRustへ渡し、状態ベクトルを直接実行する。
回路後劣化モデルでは初期回路作用と同列の非選択測定もRustの密度行列バッチへ渡し、
サンプル時刻の状態回収とRK4発展をRustのバッチ経路で行う。previewバックエンドは、
Rust拡張が未導入または対象カーネルが失敗した場合にPython参照経路へ戻り、診断へ理由を記録する。
`rust_dense_v1` はそのようなフォールバックを許可しない。

回路コンパイル、スナップショット要求の生成、イベント収集と整形は引き続きPython側の責務である。
候補状態の重複統合・優先順位・上限選択は、Rustの
`select_snapshot_indices_v1` に一括委譲する。
Rust API crateにはコンパイル実装があるが、FastAPIとシミュレーターの共通コンパイラーには
まだ接続されていない。古典分岐の実行・状態履歴の最終整形もPython側に残る。

## なぜDensity Matrixを無制限に拡張しないか

$n$量子ビットの密度行列は $2^n\times2^n$ であり、要素数は $4^n$ になる。
一方、純粋状態のStatevectorは $2^n$ 要素で済む。したがって、ノイズの有無を
無視して一つの表現に統一すると、理想回路まで不必要に指数コストが増える。

## 監査上の制約

- Statevectorはローカルゲートを直接作用させ、全体行列を構成しない。
- Rust理想Statevectorは1〜18量子ビット、Rust密度回路バッチは1〜8量子ビットに制限する。
- `binary_readout_assignment_v1` は計算基底分布へ局所的な割当行列を順に作用させ、状態行列は変更しない。
- ノイズあり回路は既存のGate-aware密度行列／CPTP経路を正とする。
- Trajectoryはまだ未実装で、診断の `trajectory_available=false` で明示する。
- 表現と状態次元は `execution_representation`、`state_dimension`、
  `density_matrix_dimension` としてAPI診断へ出力する。

これにより、将来Trajectoryを追加しても、回路エディタ・条件式・ショットUIの契約を
変更せずに実行層だけを差し替えられる。
